# Settings › MCP: adding servers

## Settings › MCP add (`lib/mcp-add.ts`, `components/McpAddServer.tsx`)
- **The browser sends the paste, never a config.** `POST /api/mcp { action: "add", text, scope, values?, secretReferences?, server?, name?, rawPi?, trustFolder?, confirmHostEnv? }` parses `text` again with the importer the pane previewed it with (`prepareMcpAdd()`), so what is written is the importer's fresh object with its escaping, and nothing the importer would have dropped can be slipped in. Values are field ids to text, escaped as any literal, or to `{ reference: NAME }`, stored as `${NAME}` (only where every target is a value pi resolves). `secretReferences` does the same for the paste's **own** literal secrets (ADR 0006's way into a project): labels from `referenceableLiteralSecrets()` (`headers.Authorization`, `env.API_KEY`, `oauth.clientSecret`: a literal secret in a value pi resolves that no field fills; one in the URL, the command or its arguments cannot be, since pi reads no variable there) to a variable name, which `fillMcpImportFields(server, values, secretReferences)` stores in place of the secret, after a header's `Bearer` / `Basic` / `Token` scheme; a bad name or place is a `field-reference-invalid` note. Checks, in order, each a typed refusal: the guards of every write (origin, JSON, cwd, `mcp-off`), the request's shape (`invalid-request`, at most 256 KiB of text), where it may go (a project server's folder, below; said first, so nothing is asked about a server the folder then refuses), the parse (`import-failed` with the importer's `notes`), the name (`name-invalid`; `name-taken` with a free `suggestedName`, checked again under the file's lock by `insertMcpServer()`), the fill (`fields-incomplete` with `notes`, secret references included), the SDK's `validateMcpServerConfig()` (`server-invalid`), `PI_WEB_PASSWORD` in a resolved value (`web-password`), a literal secret in a project server (`secret-global-only` with its `fields`, from `fillMcpImportFields()`'s `secretPaths`: typed password values included, references not; a project file is often committed), and then the host-variable confirmation.
- **Host variables sent elsewhere need a yes.** A non-pi paste (ADR 0006; `pi mcp add` and the "Enable pi mcp syntax" toggle are the user's own syntax) whose headers or `oauth.clientSecret` read variables set in Pi Web's `process.env` gets `host-env-confirm` with their `names` (`mcpHostEnvNames()`: names only, never values; a stdio entry's `env` stays in the process it starts and does not count; a variable the user named, for a field or for one of the paste's secrets, does not either). The pane shows the names and a second button that resends with `confirmHostEnv`; only names listed there count, so a paste that changed in between is asked about again.
- **A project server goes where a decision trusts the folder** (`writeTarget()`, the rule of every project write), except for a **fresh folder** (no trust-requiring resources, no decision for it or an ancestor), which `trustFreshFolderAndWrite()` (`lib/project-trust.ts`) trusts and writes in one step when the request says `trustFolder` — a plain add there is 403 `project-untrusted`. GET reports the step as `project.trustFolder` — `{ allowed: true }`, `{ allowed: false, reason: "trust-too-broad", breadth }`, or `{ allowed: false, reason: "folder-not-fresh" }` when the SDK sees nothing that needs trust but `hasTrustRelevantEntries()` finds a link to nothing where it looks — with the step's own checks in the step's order, so the pane says "Add and trust this folder" or why not before anyone presses it and never offers a step the route refuses. Inside the step:
  - **Breadth guard first** (`freshFolderTrustBreadth()`, by real path, before the paste is even parsed and again inside the step): never the home folder, a filesystem root, a folder holding the home folder or Pi's agent folder, one holding another folder Pi Web knows (the allowed file roots: session folders, their projects, folders chosen in Pi Web), or one holding a project Pi Web has never seen (`findInheritingTrustProject()`: a folder below it with `.pi/<entry>`, a dangling `.pi` link or `.agents/skills`, and no decision of its own or between, `contains-project`), since a decision is inherited by every folder below it. Fresh folders are mostly containers (`~/work`, a dated `~/pi-cwd` folder) holding cloned repositories, whose `.pi/extensions` would otherwise load and whose `.pi/mcp.json` would connect with no dialog the first time they were opened. The scan is breadth first, 4 levels deep, never through a link, `node_modules` or `.git`, and refuses (`too-many-folders`) once it has read 2,000 folders rather than trust what it did not check; it runs in GET, in the route's pre-check and again inside the chain after `getEntry()`, since a `git clone` can land in between. 409 `trust-too-broad` with `breadth`.
  - **One step per folder at a time** (a globalThis chain, `Symbol.for("pi-web:fresh-folder-trust-locks")`, keyed by the real path), and inside it the folder is **checked again**: the SDK's `hasTrustRequiringProjectResources()`, and `hasTrustRelevantEntries()`, an `lstat` of the same entries (`TRUST_REQUIRING_PROJECT_ENTRIES`, a copy of the SDK's module-private list that `lib/project-trust.test.mjs` compares with the SDK's source), a `.pi` that is a link to nothing and `.agents/skills` in an ancestor, because `existsSync` skips a dangling link that starts counting the moment its target appears; then `getEntry()` must be null. A folder that changed since the pane offered the step (a `git pull` that brought `.pi/extensions`, a decision made elsewhere, the other tab's step) is 409 `folder-not-fresh` with its new `trust`, unwritten and untrusted: trusting it then would trust what arrived, unseen.
  - **Trust first, then write.** `ProjectTrustStore.set(cwd, true)` (a locked or unparsable `trust.json` fails here, before anything is written: 409 `trust-unreadable`), then the insert; a failed insert takes the decision back with `set(cwd, null)`, which removes exactly the key the step wrote, and when even that fails the answer keeps the write's `reason` and adds `trustKept: true` with the folder's `trust`, which the pane says in words (`mcp.add.trustKept`). What the chain buys: a step that waits gets its turn once the earlier one has finished or been undone and checks the folder as that left it; unchained, it would find the earlier step's decision mid-write and be refused even when that write then failed and the decision went (`lib/project-trust.test.mjs` pins exactly that case; a second step after a successful one is refused either way, since the check and `set()` are synchronous). The pi CLI is not serialized against.
  - **Nothing is rebuilt and nothing needs to be idle**, unlike `POST /api/project-trust`: a wrapper opened in a folder that required no trust was built with `projectTrusted` true and found no project extensions to load, and its MCP host reads trust afresh before every prompt (`mayReadProjectConfigNow()`), so the server connects at the session's next message. `invalidateModelsCache()` runs after it.
- **The page learns the folder's new trust.** Every project add answers with `trust` (writing `.pi/mcp.json` alone makes a folder require trust, so even a plain add changes the status), plus `trustedFolder` for the step; a `folder-not-fresh` refusal carries it too. `McpConfig` hands it to AppShell (`onProjectTrustChanged(cwd, status)` → `handleProjectTrustChanged()`, applied only for the folder Settings shows), whose new status reloads every mounted section in place through `projectTrustReloadKey()`; no session key changes, since nothing was rebuilt.

## Paste import (`lib/mcp-import.ts`)
- Other clients store literals, but pi resolves `${NAME}`, `$NAME` and a leading `!command` in env values, header values and `oauth.clientSecret`. Literals there are escaped (`$` → `$$`, a leading `!` → `$!`); unescaped, a pasted `"!curl … | sh"` would run on the Pi Web host at every connection. `command`, `args`, `url` and `cwd` are used raw by the SDK and must never be escaped. Only `pi mcp add` and the rawPi toggle keep values as written, and a `!command` is then noted (`shell-command-value`). `lib/mcp-import.integration.test.mjs` pins the round-trip through the SDK resolver.
- References are translated into `${X}` (`${env:X}`, `{env:X}`, `%X%`, Gemini's `$X`) only in those three resolved fields. pi substitutes nothing anywhere else, so a reference in `command`, `args` or `url` becomes a field to fill in; only a leading `$HOME` / `${userHome}` becomes `~` and `${workspaceFolder}` becomes `.`. Never trust `validateMcpServerConfig` to clean an entry: it returns the object it was given and accepts milliseconds as seconds. The importer builds a fresh object from known keys, notes every dropped key, and reads a timeout in its client's unit (Gemini milliseconds, Cline seconds; a guess is a warning).
- The `pi mcp add` grammar is a port of the module-private SDK `cli.js` (`maxPositionals` 2, `-l`, an option on the wrong transport refused, splitting at the first `=`, `--help` anywhere prints help, an empty name refused). The integration test runs the real `runMcpCommand` into a temp dir and compares the written entry byte for byte, mixed shell quoting included, so an SDK change to the CLI fails the test. Quoted and unquoted text of one word is joined before any grammar reads it (`'A=$'B` is `A=$B`).
- `parseMcpImport()` and `fillMcpImportFields()` never throw: the add route (`POST /api/mcp`, action `add`) re-parses the request body, and a throw is a 500. Decode with a guarded helper (a malformed `%zz` in userinfo threw `URIError`), keep an impossible `$'\U…'` code point as text, and bound any regex run that can rescan (the `…_here` placeholder pattern was quadratic). The robustness test feeds every prefix of every sample through parse and fill.
- Literal secrets and password fields follow `lib/mcp-secrets.ts` (`literalSecretFields`, `maskArgs`, `maskUrl`, `isSecretName`), never a classifier of the importer's own: the server's `secret-global-only` refusal and the panel's masking must agree (the add preview masks none of it, only typed passwords). `fillMcpImportFields()` returns `secretPaths` (typed password values plus literal secrets) and accepts `{ reference: "NAME" }` for a field whose targets pi resolves, stored as `${NAME}` and not a secret path; `PI_WEB_PASSWORD` is the route's to refuse.
- A server name pi accepts is kept as written; only an invalid one is sanitized. A derived name avoids `takenNames`; a name the source chose that is already taken keeps its name and gets `name-taken` with a `suggestedName`, so the route can answer its typed 409.
- Command lines that manage a CLI (`pi mcp remove|login …`, `claude|codex|gemini mcp <subcommand>`, `pi install|remove|update …`) are refused with `cli-not-a-server`: imported as a stdio server, the Test after Add would run them on the host. `claude mcp serve` is a server and still imports.
- Notes are `{ code, params }` (`MCP_IMPORT_NOTE_CODES`, 84 codes with severities in `MCP_IMPORT_NOTE_SEVERITY`); a field's `label` and `description` are source data, shown as they are. The browser preview and the server re-parse run the same pure code, so client code rules apply: no regex lookbehind and no `URL.canParse` (old Safari).
