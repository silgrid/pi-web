# Settings › MCP: Test and sign-in

## Settings › MCP Test (`lib/mcp-test.ts`, `POST /api/mcp/test`)
- **The route re-checks what a session's start would** (`readConnectableMcpEntry()` in `lib/mcp-entry-request.ts`, which sign-in shares), because Test starts a process or contacts a URL and may run a `!command`: origin (403 `request-denied`), JSON (415), `{ scope, name }` (400 `invalid-request`), the cwd as GET checks it (`cwd-*`; required for a project server), then MCP off — `PI_WEB_DISABLE_MCP` or SDK modules that cannot load (409 `mcp-off`), but not `-builtin:mcp`, under which Test stays an explicit action — and for a project server a decision, exact or inherited, that trusts the folder (403 `project-untrusted`, 409 `trust-unreadable`; the host's `mayReadProjectConfigNow()` rule, never `trusted`). The entry is read from its file by `readMcpServerEntry()` (`lib/mcp-config-read.ts`, the listing's parse and link rule: a file problem is its 409, an absent name `server-missing`, looked up among the parsed entries so `__proto__` is just a name), never taken from the browser, then must be an object (409 `entry-not-object`), pass `validateMcpServerConfig()` (409 `server-invalid`, new) and not reference `PI_WEB_PASSWORD` (409 `web-password`). A switched-off entry can be tested before it is turned on. A global stdio server runs in the panel's project when the request names one (checked like any cwd), else in `homedir()`; the result names the folder. That folder is also the MCP root the server is sent.
- **Connecting is a session's connection**: the SDK's `McpServerConnection` with `createPiWebMcpTransportFactory()` (scrubbed env, `inheritEnv: false`) wrapped to capture every transport, and the SDK's `McpOAuthCredentialStore` (`mcp-auth.json` in the agent dir, which a test of an OAuth server creates as a session would), guarded for an OAuth entry so a sign-out during the test bars its writes and its record (see **Settings › MCP sign-in**). A 401 with no stored token reads `needs-auth`.
- **Bounded at every step, since a response must never wait on a close.** Each request gets min(the entry's `timeout`, 15 s) (`MCP_TEST_REQUEST_TIMEOUT_MS`, a copy of the entry; the SDK default is 60 s). The test has a 20 s deadline (`MCP_TEST_DEADLINE_MS`), aborted early once every caller's request signal has (refcounted: a press joined by another tab keeps it alive). On abort it calls `connection.close()` (marks it closed before its first await, which also ends an HTTP retry between attempts) and **closes the captured transports directly**: that fails the pending handshake at once, while `connection.close()` alone leaves a stdio child running until its request times out. Closing is awaited only `MCP_TEST_CLOSE_WAIT_MS` (2 s): `StdioTransport.close()` waits for the child's `close` event, which a grandchild outside the process group can hold off for good, and `connection.close()` waits for an OAuth refresh; both carry on in the background. The SDK's own `connectOnce()` awaits `client.close()` inside a failed attempt, so even a plain failure of a SIGTERM-ignoring server takes up to the 2.5 s SIGKILL; the deadline race covers that too. Read the connection's `state` before closing it: `close()` sets it to `closed`. **Closing is in a `finally`**: building the result must never leave a stdio server running, and pi-mcp checks only a listed tool's `name` and `inputSchema`, so `describeTool()` reads `description` / `title` / `annotations` only where they are strings (a numeric description used to throw, answer 500 and leak one process per press). The SDK's `getMcpToolExposure()` indexes `toolExposure` plainly, so a tool named `constructor` got `Object.prototype`'s function as its exposure; `toolExposure()` passes it a prototype-free copy and falls back to the server's exposure for anything but the five values. An injected `connect` that ignores the abort is still cut off `closeWaitMs + 500` after it.
- **`!command` entries run one at a time.** A `!command` runs synchronously (`execSync`, up to 10 s) and blocks the event loop, deadline timers included, so nothing interrupts one. Tests of entries whose resolved fields hold one (`runsShellCommand()`: a stdio entry's env, an HTTP entry's headers and `oauth.clientSecret`; an env on an HTTP entry runs nothing) wait in a globalThis promise chain (`Symbol.for("pi-web:mcp-test-command-queue")`) for at most the deadline again; one that never got its turn answers `queueTimedOut` and is not recorded. A test that gives up its place releases it at once without letting the next jump the ones ahead. Presses on the same entry (scope, file, name, `configKey`, cwd) join the test under way (`Symbol.for("pi-web:mcp-test-flights")`). A test every caller gave up on leaves that map at once, while it still closes, so a press in that window starts a new test instead of joining one that can only answer "no answer" and record nothing.
- **Nothing literal reaches the browser.** The SDK quotes a failed `!command`'s text (`Failed to resolve … from shell command: <text>`), and a server may echo its env, its key or its URL, so `createTestRedactor()` masks, in `error`, `stderr`, the tool names and descriptions and `serverInfo` (all server-written text): a `!command` text wherever the SDK quotes it after `from shell command: ` (any length; the SDK discards the command's own stderr, so nothing else can print it) and elsewhere as a word from 6 characters; literal env / header / `oauth.clientSecret` values and what the transports resolved them to (the entry's own env names only; the rest is the host's sanitized env); the command, arguments and URL as GET masks them; and the parts those masks hide, also where a message quotes one on its own (`urlSecretParts()` / `argSecretParts()` / `commandSecretParts()` in `lib/mcp-secrets.ts`: a query value, a userinfo password, a flag's value, each also percent-decoded) and the URL as `new URL().href` spells it. Values shorter than 6 characters stay, so `1` or `true` cannot garble a message. A whole secret is replaced wherever it appears; a word split from a value (`Bearer <token>`) or a command text only where it is not part of a longer word, so `!gh auth token` leaves "authentication" alone and `!env` never masks the SDK's own `env "TOKEN"`. **Mask, then shorten:** `error` keeps its first 2,000 characters and `stderr` its last 2,000 (the transport keeps 64 KiB), each masked over a 64 KiB window first, so a cut never leaves half a secret; an `error` used to be unbounded (a JSON-RPC error may be 16 MiB) and sat in the status store, sent with every GET. The SDK appends the stderr tail to its message; `splitStderr()` moves it to `stderr` at the first line break whose remainder is part of the transport's stderr.
- **Status store** (`lib/mcp-status.ts`, `Symbol.for("pi-web:mcp-status:by-config")`). A test records `{ origin: "test", ...result }` under `scope\0sourcePath\0name` with the entry's `configKey` (`mcpConfigKey()`, the HMAC GET reports), unless every caller gave up before it settled. Each entry holds one record per `configKey`, never one in all: a writer behind the file (a session that has not synced an edit yet) must not replace the record for the entry as it is now, which the next read would then drop as stale. `readMcpOverview()` attaches the record whose key matches the file and deletes the entry's others (an edited entry reads untested, even once edited back), records of a file read without a blocking problem whose name it no longer defines are pruned, and the map holds at most 500 records, the oldest of the entry written longest ago first out. Session hosts write theirs too (see **MCP host** in [mcp-runtime.md](mcp-runtime.md)), and so does a sign-in (`afterSignIn` on the reconnect after it, see **Settings › MCP sign-in**); the latest write for the same content wins. The symbol changed name with that shape: a dev server keeps `globalThis` across hot reloads, and the new code would otherwise read the old map. Any later change of a globalThis store's shape needs a new name for the same reason.
- **The panel** gives each server a **Connection** row right under Status: the last status (`connected` with its tool count and time, `needs-auth`, `failed` with the SDK's message and a scrolling `<pre>` of stderr, a timeout as "No answer"), the server's name and version, its resources, and for stdio the folder it ran in; then why Test cannot be used (`mcpTestBlock()`: the write blocks `mcp-off` / `project-untrusted` / `trust-unreadable`, then `invalid`, `web-password`) as visible text that the disabled button, which sits in the detail header before Remove (`McpTestButton`), points at with `aria-describedby`; an entry with a `!command` field (env, header or `oauth.clientSecret`) adds that its tests wait for other such tests; "No answer" says Pi Web stopped the test, not the server, which for HTTP it only stopped waiting for. A connected test adds a read-only **Listed tools** row: each name, a `read-only` tag for `readOnlyHint` (what read-only sessions require), its exposure where `toolExposure` makes it differ from the server's, and the description's first line. A test writes no file, so it never sets `busy`: switches, Remove and Refresh keep working, and one test per server runs beside them. Each answer is kept per server (`McpTestRun`) and shown over the listing's status while it is about the entry shown (same `configKey`) and newer (`mcpWithTestResults()`), so a load already on its way cannot hide it; a Sign out that worked drops the kept answer, and an answer to a test sent before it (`startedAt` ≤ `signedOutAt`, `mcpTestRunAfterSignOut()`), since the route forgot the entry's statuses and the old answer would otherwise read Connected until Settings closed; a failed request or a queue timeout keeps the last result beside a `role="alert"` line, worded as a test's (`MCP_TEST_REFUSAL_KEYS`: also the file problems, `entry-not-object` and `invalid-request`, whose `mcp.reason.*` wording speaks of writes) rather than a change's, and carries the `configKey` it was about (`mcpTestRunFor()` hides it for an entry edited since). **An answer that shows the listing is stale loads it again** (`mcpTestAnswerOutdates()`), as a refused change does: any refusal with a reason, or an answer for another `configKey` than the listed one (edited outside the panel), whose result the listing would otherwise never show. **Test requests are never aborted** — not when Settings closes, not at the client's 60 s wait (`MCP_TEST_TIMEOUT_MS`: deadline, queue, close and a blocking `!command`; `withinDeadline(…, { abortAtDeadline: false })`): Next aborts `req.signal` when the request is aborted, and the route stops a test nobody waits for and records nothing, so an aborted request would lose the result the "press Refresh" message promises. Only closing the page stops one. Test is disabled while it runs, so it takes focus back once answered (`focusIfLost()`).
- Tests: `lib/mcp-test.test.mjs` connects the env fixture (tools, `readOnlyHint`, `toolExposure`, `serverInfo`, PI_WEB_PASSWORD absent from the child's env via `PI_WEB_FIXTURE_ENV_FILE`), stops `lib/__fixtures__/mcp-hang-server.mjs` (never answers, ignores SIGTERM, but exits by itself once re-parented or after 30 s, so an interrupted run leaves nothing behind) within the deadline plus margin and checks the process is gone, caps a 120 s `timeout`, reads a local HTTP 401 with `WWW-Authenticate` as `needs-auth`, masks a failing `!command`'s text, reads only string tool fields and closes the server either way (`PI_WEB_FIXTURE_ODD_TOOLS`), masks an oversized error before shortening it (`PI_WEB_FIXTURE_INIT_ERROR`), pins the redactor (quoted command text, word-bounded words, URL and argument parts on their own), and pins the queue, joining, cancellation (a press after everyone left starts afresh) and the queue timeout with an injected `connect`. `app/api/mcp/test/route.test.mjs` runs the route against a temp `PI_CODING_AGENT_DIR` (and a temp `HOME` where a global server starts without a project, with `PI_WEB_PASSWORD` set so its absence from the child's env means something): guards, untrusted 403 with the `!touch` never run, `PI_WEB_DISABLE_MCP`, the refusals, no literal secret in an answer, and a status GET drops once the entry is edited.

## Settings › MCP sign-in (`lib/mcp-sign-in.ts`, `/api/mcp/sign-in`)
- **It runs as `pi mcp login` does** (SDK `extensions/mcp/cli.js` login()): connect once through the same connection a Test opens (`openTestConnection()` / `observeTestConnection()` / `closeTestConnection()` in `lib/mcp-test.ts`, kept open) to learn whether the server asks for a sign-in and to record its challenge; already connected ends `done` (`alreadySignedIn`), any other failure `failed` (`connect-failed`); then the SDK's `signInMcpServer()` with `connection.oauthSettings()` (resolved while the entry's place in the `!command` queue is held: `oauth.clientSecret` may be one), the challenge and a prompt; then `connection.reconnect()` with the new tokens. Each connect has the test's deadline once it has its turn in the queue, never across the wait for the browser. Only an HTTP entry without an `Authorization` header signs in (`mcpOAuthUrl()`, the SDK's `usesOAuth` rule; the integration test pins it against `connection.oauthUrl`), else 409 `sign-in-not-oauth`.
- **The flow outlives every request.** `POST /api/mcp/sign-in` runs the route checks a Test runs (`readConnectableMcpEntry()`), starts the flow and answers at once with it; the panel then polls `GET /api/mcp/sign-in/[flowId]` about once a second. Flows live in a globalThis registry (`Symbol.for("pi-web:mcp-sign-in")`) under a `randomUUID()` id, with unref'd timers, and nothing ties one to a request signal or a stream (the provider login route aborts its flow when its SSE closes, so it could not be reused): a sleeping phone or a closed Settings loses nothing, and pressing Sign in again joins the flow.
- **One flow per server URL per process** (keyed as `mcp-auth.json` keys it, `String(new URL(url))`): the SDK keeps one PKCE verifier and one `state` per URL in that file, so two sign-ins of a URL overwrite each other's and both fail with `invalid_grant`. A second start, from another entry of the URL or another tab, joins (`joined: true`; the flow names the entry that started it, and the reconnect's result is recorded for that entry only, so the joining row's ending names that entry and sends the user to Test connection instead of pointing at its own Connection row: `mcpSignInShared()`, `mcp.signIn.shared.*`). A flow of a URL whose previous run is still unwinding (cancelled or expired while a network request had not answered) waits for that run before it connects. A `pi mcp login` in a terminal is not serialized against.
- **Five minutes, and the SDK cannot be aborted.** `signInMcpServer()` takes no AbortSignal, and its loopback callback gives up after 5 minutes (pi-mcp `OAuthCallbackServer`). The flow expires `MCP_SIGN_IN_TTL_MS` (5 minutes) after it starts, so first; the only way to stop the SDK is to answer its `promptForRedirectUrl()` with "" (McpSignInCancelledError). A cancel or an expiry answers a waiting prompt at once; one that arrives before the SDK asks (discovery still running) is kept and answered the moment it asks; one before `signInMcpServer()` was called stops the run there. An ended flow stays readable for `MCP_SIGN_IN_KEEP_MS` (60 s), then `GET` answers 404 `sign-in-unknown`. Discovery, registration and token requests have no timeout of their own (undici's defaults apply), so a run can outlive its flow; it then changes nothing about the flow.
- **A pasted address is checked first**, since the SDK ends the whole sign-in on a bad one: `pasteMcpSignInRedirect()` refuses with 400 and leaves the flow waiting when the text is not a URL (`redirect-invalid`), carries another `state` (`redirect-state-mismatch`; compared with the `state` the SDK stored last, watched through the store it is given, which is the one it checks against, the page's own `state` only as a fallback), is an `error=` answer (`redirect-denied`, with the server's description as `error`), or has no `code` (`redirect-no-code`); a paste while nothing waits is 409 `sign-in-not-waiting`. The loopback callback (a browser on the same computer) finishes the flow with no paste: the SDK then aborts the prompt's signal, which moves the flow to `finishing`.
- **No browser at all is a normal ending**: a stored refresh token renews the tokens inside `signInMcpServer()`, which never shows a page (`refreshed`). Starting a sign-in may also delete the stored client registration and tokens (the SDK drops a registration whose redirect URI is not the new one), so the panel says so beside the button.
- **What it records.** The first connect's result is the entry's status, as a Test's would be (`needs-auth` while the browser is awaited); the reconnect's is recorded with `afterSignIn: true`, which the Connection row sums up in sign-in words (`MCP_SIGN_IN_SUMMARY_KEYS`). An open session's own record stays `needs-auth` until it reconnects at its next turn, and the sign-in's record is the newer one. Errors go through the test's redactor plus the resolved client secret (`createTestRedactor(…, resolvedSecrets)`). Before the reconnect, which may come minutes after the route's checks, the route's `mayConnect()` asks again whether a project entry's folder is still trusted (and MCP not off); if not, the flow ends `done` without connecting.
- **Sign out** is `POST /api/mcp { action: "sign-out", scope, name }`: the URL is read from the entry's file under the checks of any change to it (a project entry's folder must be trusted), the SDK store's `remove(url)` deletes the URL's tokens and client registration (`pi mcp logout`), a missing `mcp-auth.json` is not created to find nothing in it, and the entry's status records are forgotten (`forgetMcpEntryStatuses()`), since signed-out connections no longer see what they found. Open sessions read the store on every request, so they lose access at their next one (a refresh one of them already has on its way can still write its tokens back, as with `pi mcp logout`). The answer is the overview plus `signedOut: { scope, name, removed }`.
- **Signing out bars every run of the URL from writing, before it removes anything.** Cancelling is not enough: a cancel only answers a prompt that still waits, while a code exchange (a pasted address, the loopback callback) or a refresh (`signInMcpServer()`'s, or the connection's own during a connect) that is already on its way stores its tokens whatever happens to the flow, which signed the URL back in right after the removal while the panel said "Signed out". So `signOutMcpServer()` first counts a sign-out for the URL key (`noteMcpSignOut()` in `lib/mcp-sign-out.ts`, under `Symbol.for("pi-web:mcp-sign-outs")`, which takes over the map an older dev-server registry held as `signOuts`), then cancels the active flow, then removes; every run writes `mcp-auth.json` only through stores that call its `McpSignInWriteGuard` before each write (the SDK sign-in's store through `watchedStore()`, the connection's through `guardedCredentialStore()`, a subclass of the SDK's store passed to `openTestConnection({ credentials })`), which throws `McpSignedOutError` once the count moved since the flow started. The SDK's writes are synchronous, so the check and the write cannot be split by the removal. A run started after the sign-out writes normally. Waiting for the run to unwind instead would not do: its network requests have no timeout of their own. **A Test is such a run too**: an OAuth entry's test connection gets `guardedCredentialStore()` with a guard taken when the test starts (`mcpSignOutGuard()`), so a refresh it has on its way when the URL is signed out (an expired access token is refreshed before the first request, up to 15 s per request) stores nothing; its result is then not recorded, since the sign-out forgot the entry's statuses, and the URL's sign-out count is part of the flight key, so a press after a sign-out never joins a test started before it.
- **The panel** (`components/McpSignIn.tsx`, in an HTTP server's Sign-in row): the signed-in hint, Sign in (primary) and, unless `mcp-auth.json` holds nothing for the URL, Sign out (`oauthStateStored`: any record under the URL key, which includes the client registration and PKCE state a cancelled or expired sign-in leaves without tokens and which Sign out removes as `pi mcp logout` does; `signedIn`, an access token, only words the hint); while a flow runs, its phase as a `role="status"` line and Cancel instead (disabled in `finishing`, the authorization server having answered, with a visible line saying so that Cancel's `aria-describedby` points at). Sign in waits while a Sign out of the row is on its way, which would cancel it on arrival. In `authorize`, `OAuthPastePanel` is always shown with the page as a link (only an `http(s)` URL becomes a link: the page comes from the server's metadata), the address the browser is sent back to, and the 5-minute limit; the box is never focused by itself (a phone keyboard would cover the link), has an accessible name, waits while a paste is checked, and submits from its button or Cmd/Ctrl+Enter, never a plain Enter (`plainEnterSubmits={false}`, the cross-cutting paste-box rule; Models' subscription box keeps plain Enter); no Enter submits while an input method composes (`oauthPasteKeySubmits()`). A failed cancel's or a refused paste's line goes once a poll reads the flow ended. Blocks (`mcpSignInBlock()`, the Test route's; `mcpSignOutBlock()`, the write blocks and a refused entry) are visible text the disabled buttons point at. The Connection row's needs-sign-in words never send the user to `/mcp` in a chat. "Signing in may replace what is stored for this URL" shows only while something is stored (`offersSignOut`). A sign-in writes no `mcp.json`, so it runs beside changes like a Test; Sign out goes through `runAction()` (`sign-out:<key>`). When a polled flow ends (`mcpSignInJustEnded()`), the overview is read again. Starting is never aborted (`postMcpSignIn()` leaves the request running at its 15 s deadline, as `postMcpTest()` does), and closing Settings stops only the polling.
- Tests: `lib/mcp-sign-in.test.mjs` drives the registry with a stub connection and `signInMcpServer` (phases, every paste refusal keeping the flow, the stored state, the loopback callback, refresh without a page, already signed in, connect failures, masked errors, cancel before the run / before the page / while waiting, expiry and forgetting, joining, a run waiting for the previous one, no poller, `mayConnect`, the resolved `oauth.clientSecret` masked by the connection's own `redact()`, sign-out, and a sign-out barring a code exchange or a cancelled run's refresh still on its way while a sign-in started after it stores normally, with `guardedCredentialStore()` over the SDK's own store); `lib/mcp-sign-in.integration.test.mjs` runs the SDK's own flow against `lib/__fixtures__/mcp-oauth-server.mjs` (a local MCP server and authorization server with registration, PKCE and refresh tokens) in a temp `PI_CODING_AGENT_DIR`: a pasted address, the loopback callback, already signed in and a connection-side refresh, a cancel closing the loopback listener, sign-out, and a sign-out while a sign-in's or a Test's refresh is held at the token endpoint (`hooks.beforeRefresh`) storing nothing; `app/api/mcp/sign-in/route.test.mjs` covers the routes' guards, 404s, refusals, an untrusted project's `!command` header never run, a project sign-in finished after trust is revoked or MCP is turned off ending without the reconnect (the route's own `mayConnect()`), joining, and the sign-out action. Never sign in against a real server or a real `mcp-auth.json`.
