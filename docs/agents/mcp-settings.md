# Settings › MCP: reads, panel and writes

## Settings › MCP reads (`lib/mcp-config-read.ts`)
- `GET /api/mcp` reads files only: it never spawns a server, opens a connection, or resolves a value, so it lists an untrusted project as safely as the global file. Nothing on its path may call `createDefaultTransport()`, `resolveConfigValueOrThrow()` / `resolveHeadersOrThrow()`, `connection.oauthSettings()` (each runs `!command` values) or `McpOAuthCredentialStore` (a read creates `mcp-auth.json` and a lock); the route test pins that a `!touch` value never ran and that the agent dir holds nothing new afterwards. The signed-in hint is a raw parse of `mcp-auth.json`, keyed as the SDK keys it (`String(new URL(url))`), with tokens meaning `tokens.access_token`; an unreadable file leaves `signedIn` unset, not false. Reading `trust.json` still takes the store's `lockSync` (a transient `trust.json.lock` directory), and the Code mode preference the settings lock, like every other reader.
- Each file is read on its own, never through `loadMcpConfig()`: that skips an untrusted project's file and merges by name, hiding the global entry a project entry replaces. The text is parsed as the SDK parses it (`JSON.parse`, no BOM stripped, `{ mcpServers: {} }` shape, `autoEnableCodemode` a boolean) and each entry checked with the SDK's `validateMcpServerConfig()` when the internals load; an invalid entry is still listed with the SDK's reason. Without the internals (MCP off) entries are listed unvalidated (`validated: false`), a leading `!` marks a command, and any mention of `PI_WEB_PASSWORD` counts. A global entry is `shadowedByProject` only when the project's entry would load: the SDK skips an invalid one and keeps the global. The contract test checks that, on a trusted merge, the per-file reader gives exactly `loadMcpConfig()`'s servers.
- The **project file** is repository-controlled and read before anyone trusts it, so it follows the file-access rule for links: its real path (a link in the file or in `.pi/` above it) must be inside the allowed roots the route already checked the cwd against, a dangling link is refused (`link-dangling`) rather than read as no file, and the resolved path is opened once with `O_NOFOLLOW | O_NONBLOCK`, checked through `fstat` (regular file, at most 1 MiB), so a FIFO is never read. A project file declaring more than `MCP_PROJECT_MAX_SERVERS` (200) servers is reported as `too-many-servers` and none of them is listed, as one over 1 MiB is: 80,000 names fit in 1 MiB, and describing each cost seconds and a 32 MB answer, in the panel and in the trust dialog. The **global file** is the user's: a link is followed wherever it leads (`realPath` reports where) and a dangling one reads as no file, as for the SDK. A trusted project's link outside the roots is still followed by the SDK when a session connects — the panel can only report `link-outside`.
- Nothing literal reaches the browser: env and header **values** are never sent (names only), `command`, `args` and `url` go through `lib/mcp-secrets.ts` — except `command` and `args` of a project no decision trusts (`projectUntrusted`, `trust.decision !== true`, in the panel and the trust dialog alike), shown as written because the masking rules let the repository's author pick what is hidden of what trusting it would run; its URL is still masked, and never its host — (userinfo, query parameters named like credentials or holding token-like values, bare token-like query parts and path segments, `--api-key=…` / `--token X` / `-k X` / `--auth X`, `Name: value` headers, `NAME=value` pairs and `Key=value;…` connection strings), and a value of several words — a whole command line in `command`, `Bearer …` as one argument — is masked word by word, where `Bearer` / `Basic` / `Token` or a credential `Name:` makes the next word a secret: checking only whitespace-free values left a spaced token whole. Those three fields are used as written (the SDK expands nothing there), so only placeholder-shaped values are kept as references: `${NAME}`, or `$NAME` in environment-variable capitals, which a wrapper such as mcp-remote or `sh -c` expands; `$Passw0rd` is masked. The fields the SDK resolves (env, headers, `oauth.clientSecret`) use `isReferenceOnly()`, the SDK's own syntax (`$name` of any case, `$$` / `$!` escapes). A JSON syntax error never quotes the file: for an unexpected token V8 quotes up to ten characters on either side instead of giving a position, which is how a single-quoted secret leaked, so the message keeps the token only when it is punctuation and gives the position that context stood for (`Unexpected token ''' in JSON at position 65 (line 1 column 66)`); messages that already give a position quote nothing and are kept. `configKey`, which later statuses compare against, is an HMAC of the entry's canonical JSON (`canonicalJson()`, total: an array or object past 64 levels prints as a marker instead of being followed, since a 6 KB repository file nested thousands deep overflowed the stack, stopped every server of the session's sync and made GET answer 500) under a random per-process key (`mcpConfigKey()`, both in `lib/mcp-config-key.ts`, which the MCP host imports too), never the JSON: that would carry every literal value, and a plain hash would not survive a weak password in an otherwise visible entry. `lib/mcp-secrets.ts` is pure, for the browser-side importer too; its `literalSecretFields()` is the same classification for deciding what may only be saved globally.
- `commandFields`, `variableReferences` and `webPasswordField` come from `resolvedConfigValues()` in `lib/mcp-transport.ts`, the walk the transport itself refuses `PI_WEB_PASSWORD` with: a stdio entry's `env`, an HTTP entry's headers and `oauth.clientSecret`, told apart by whether `url` is present. An `env` on an HTTP entry is never resolved, so a `!` there runs nothing and is not labelled. `transport` and `usesOAuth` follow the same rule, not the validator's branch: `{ type: "stdio", command, url }` validates as stdio but `createDefaultTransport()` connects it over HTTP and runs its header `!command`s, so it is reported as HTTP. Only an entry the validator refuses, which never connects, gets the validator's reading (a legacy SSE entry has no transport). `variableReferences` names the host variables each of those values reads (`${NAME}` / `$NAME`, through the SDK's `getConfigValueEnvVarNames()`, or `templateVariableNames()`, a port pinned against it, when internals are unavailable), never their values: they resolve from Pi Web's whole `process.env`, not the sanitized one a stdio server starts from, so a header `${GITHUB_TOKEN}` sends that token to the entry's URL. A `!command` value is in `commandFields` instead.
- Availability is a typed reason, checked in this order: `operator-disabled` (`PI_WEB_DISABLE_MCP`), `internals-unavailable` (with the loader's `detail`), `builtin-disabled` (with the `settingsPath` whose `extensions` entry does it). `readBuiltinExtensionSwitches()` in `lib/builtin-extensions.ts` asks the SDK's `DefaultPackageManager` with only the two `extensions` lists (the project's only while trusted) and `onMissing: skip`, so `-builtin:mcp`, project `+`/`-` overrides and `!builtin:*` patterns resolve exactly as the resource loader resolves them, and no package is ever installed or looked up; it still scans the auto-discovered resource folders, read-only. Code mode reports the global preference, `-builtin:codemode` likewise, and `peekCodemodeSandbox()`: the settled self-test result, or `not-checked` while no normal session has run it since the server started — it never starts the self-test. With a cwd whose settings sessions load (`trust.trusted`, the rule `projectTrustReloadOptions()` applies when a session starts, inherited trust included; an unreadable store, never), `projectOverride` names the project's `.pi/settings.json` when its `defaultTools` decides Code mode there whatever the global choice: a list with a plain name replaces the global list, `+codemode` and all, and a modifier-only list is appended to it, so a `+codemode` / `-codemode` in it has the last word. `projectCodemodePreference()` (`lib/codemode-settings.ts`) does not reimplement that merge: it hands the project's raw text to the SDK's own `SettingsManager` twice, once beside each global choice, and an override is exactly the two agreeing, malformed values included (pi resolves `"defaultTools": null` to no tools at all). The file is read without pi's lock, as `readBuiltinExtensionSwitches()` reads it. Both reads of a trusted project's `.pi/settings.json` go through `readRegularFileText()` (`lib/regular-file.ts`): opened once with `O_NONBLOCK`, checked through `fstat`, at most `PROJECT_SETTINGS_MAX_BYTES` (1 MiB). A plain `readFileSync()` waits on a FIFO until something writes to it and, being synchronous, stalls the whole server; the switches read came first in the same GET, so guarding only the Code mode read left GET hanging. A file that is not regular (or too large) throws in the switches read, which the overview already treats as an unreadable file (every built-in on), and reports no override.
- `ProjectTrustStatus` also carries the nearest decision (`decision`, `decisionPath` as `trust.json` keys it, and `inherited` when that is an ancestor, compared by real path with `samePath()`), so exact trust, trust through a parent, an explicit `false` and no decision at all can be told apart, the last also for a fresh folder (`requiresTrust: false`). Reading it for a folder that requires no trust is new, and such a folder never failed on a broken `trust.json` before, so that failure goes to `decisionError` instead of throwing; a folder that requires trust still throws. `mayReadProjectConfigNow()` and `projectTrustReloadOptions()` do not need the decision and check `hasTrustRequiringProjectResources()` first, so neither locks `trust.json` for a fresh folder on every prompt or session start. `trustProject()` builds the status it returns from what it wrote instead of reading `trust.json` back: a second read can fail on the lock, and `POST /api/project-trust` would then answer 500 for a decision already on disk and skip rebuilding the cwd's wrappers.
- **The trust dialog lists the project's MCP servers** (`components/ProjectTrustDialog.tsx`), the visibility ADR 0006 traded per-entry approval for. `GET /api/project-trust` adds `mcpFile` and `mcpServers` to the status: `readProjectMcpServers()`, the same file-only read and masking as `/api/mcp`, filtered to the project's entries, where `replacesGlobal` marks one that replaces a global server of its name once trusted (the counterpart of `shadowedByProject`). Each entry shows its command line or URL, its `!command` fields, the host variables it reads (worded "sends … to this server" for HTTP, which is how a repository exfiltrates a token through a header) and, for `PI_WEB_PASSWORD`, a warning rather than a reassurance: Pi Web refuses such an entry, but the pi CLI reads the same file and does not. A refused entry shows neither line, since it never connects. AppShell's page-load fetch of the same route gets the listing too and ignores it; the dialog fetches it again when it opens, since the file can change in between, and hands the fresh status to AppShell (`onStatus`), so a folder trusted meanwhile, or no longer needing trust, is told so and not offered Trust. Trust stays disabled until that listing answers (`MCP_LISTING_TIMEOUT_MS`, 10 s), so the list cannot appear under a click already on its way; a listing that fails or times out stops holding it back. The listing never depends on `trust.json`: when the store cannot be read (unparsable, or locked past its ~200 ms wait while the pi CLI writes), GET answers 500 `trust-unreadable` with the listing beside it, otherwise the dialog would enable Trust with nothing listed and a later click would trust the folder unseen. A project file reported `link-outside` or `too-large` is not listed, yet the SDK reads it anyway once the project is trusted (it follows links and has no size cap), so those problems say so in the dialog rather than reading as "no servers". Every refusal carries a `reason` code (`cwd-invalid`, `cwd-not-directory`, `cwd-denied`; POST adds `request-denied` 403 and `content-type` 415 as the plugins route checks them, `trust-not-required` and `session-busy` 409, `internal` 500); AppShell keeps `{ error, reason }` and the dialog renders `mcp.reason.<code>`, showing the English `error` only as the diagnostic of an `internal` or network failure. Repository text (name, command, arguments, cwd, URL, field names) goes through `revealHiddenCharacters()` in `lib/mcp-server-display.ts`: controls, format characters (bidi overrides, zero-width), separators, variation selectors, blank fillers and every space but U+0020 become `\u{XXXX}` (never `\n`, which a Windows path like `C:\new` would collide with), an argument holding one is quoted, and the entry gets a warning line; the CSS keeps `white-space: normal`, so a run of spaces cannot push a value's tail out of view either. The command is quoted like an argument: the SDK spawns it with `cross-spawn` and no shell, so `./tools/lint --check` is one file name. Strings: `trust.mcp.*` for the dialog, and the shared `mcp.transport.*`, `mcp.field.*`, `mcp.server.*`, `mcp.fileProblem.<reason>` and `mcp.reason.<code>` keys, which Settings › MCP reuses instead of adding its own. Layout lives in `app/settings.css` (`.project-trust-*`), never inline: only the body scrolls, the trust error and buttons sit outside it, and the backdrop pads with the safe area, plus the iOS standalone fallback Settings uses. The dialog is offered only while `requiresTrust && !trusted` (by the restricted-mode banner, and by Settings › MCP's trust notice, which opens it above Settings), so a project trusted through an ancestor never shows it; Settings › MCP is where those servers are visible.

## Settings › MCP panel (`components/McpConfig.tsx`)
- **No project needed.** `mcp` is a settings section but not one of `PROJECT_SECTIONS`: without a project the panel lists the global `mcp.json` alone, and a project adds its group. `settingsSectionRequiresProject()` in `lib/settings-navigation.ts` is the one place that decides which sections need a project; SettingsPanel's tabs, the phone picker, the effect that falls back to General and AppShell's sidebar shortcuts all read it (the effect used to hard-code skills/agents/plugins, the shortcuts `section !== "models"`). The panel mounts with or without a cwd, keyed on `cwd ?? ""` so a project change remounts it, and remembers its row per project (`["mcp", cwd]`) or under the bare `"mcp"` key without one.
- **Sidebar.** The Code mode row comes first, so the 190px phone sidebar always shows it; then Project (only with a cwd, kept when its file is missing or the route refused the folder, so the panel says where project servers would come from) and Global, each with its `n/m` count beside the group switch (`ConfigSidebarGroupSwitch`, see **Settings › MCP writes**).
- **Row states come from the files first** (`mcpServerRowState()` in `components/mcp-config-helpers.ts`), most important first: `invalid` (pi refuses it), `web-password`, `disabled`, `not-trusted`, `replaced`, `mcp-off`; only an entry the file lets connect then shows its last known status (`mcpStatusRowState()`), `connected`, `needs-auth` or `failed` from a test (see **Settings › MCP Test** in [mcp-test-sign-in.md](mcp-test-sign-in.md)) or a session, and from a session also `connecting`, `disconnected` and `conflict`, else `on`. A session's `not-trusted` reads `on` there: it saw an older trust than the listing, which says the file is read now. So does a connection the session closed since (`closedAt`), whose Connection row says when it closed in a neutral tone. Every status time shows its date when it is not today's (`mcpStatusTimeText()`): records last as long as the server process. Where a test's and a session's words differ the label says where it was seen (`mcpRowStateLabelKey()`: "Connected in a session", not "when tested"); the Status row adds a sentence (`mcpRowStateDetailKey()`) only for states the Connection row does not report (`connected`, `needs-auth`, `failed` and `connecting` get none), and the Connection row shows a session's report as its state, the folder of the session that made it, the time, and the error and stderr, or the extension that holds the name (`McpSessionStatusLines`). Listed tools come only from a test. `on` means a session would connect it, never that one did. Project servers count as read only while `trust.decision === true`, the MCP host's `mayReadProjectConfigNow()` rule, never `trust.trusted`, which is true for a folder that requires no trust; a global entry reads `replaced` only while the project's entry is read in its place. The status dot is `aria-hidden`, so each state is in the row's `aria-label`, in a short visible badge (all but `on` and `connected`, which need nothing done, and `mcp-off`, which the banner says once), and in the detail pane.
- **Notices.** MCP off, with its reason (`operator-disabled`, `internals-unavailable` with the loader's detail, `builtin-disabled` naming the settings file). Otherwise, an open session whose `/mcp` is another extension's (`hostInactive`), naming its folder and that extension: only a session can tell, since it takes loading the extensions. A project folder the route refuses (`cwd-*`) does not hide the global servers: `loadMcpOverview()` loads again without the cwd and the Project group says "Not listed" under a notice with the translated reason. Trust is reported only when the project has a `.pi/mcp.json` or a problem with one: untrusted through `ConfigTrustNotice` (with Trust… where the dialog would offer it, see below), an inherited `false` naming the folder it was recorded for, and inherited trust as "Trusted through <path>": the trust dialog never opens for a project trusted through a parent, so this is where that trust is visible. A folder that requires no trust gets no trust notice unless a decision marks it untrusted: the reader lists a `.pi/mcp.json` that is a dangling link (`link-dangling`), but the SDK's `existsSync` follows the link, finds nothing and has nothing to trust, so a Trust button would only meet `trust-not-required`. File problems go to the footer (`ConfigFooterStatus` details: path, translated reason, and `mcpFileProblemDetail()`'s diagnostic), and with nothing listed the detail pane says a file problem hides the servers instead of "No MCP servers yet". A load ends after `MCP_OVERVIEW_TIMEOUT_MS` (15 s, both requests together) with a translated timeout, since Refresh is disabled while one runs; the caller's abort signal is forwarded by hand, as `AbortSignal.any()` needs Safari 17.4.
- **The detail pane shows only what GET sends:** the masked command line (`mcpServerTarget()`), the working directory and env and header **names**, each only when the entry sets it (no "None" rows), the `!command` fields ("Runs a shell command on every connection") and host variables (both left out for a refused entry, which never connects; a disabled one keeps them, since it would run them once on), the Sign-in row (see **Settings › MCP sign-in** in [mcp-test-sign-in.md](mcp-test-sign-in.md)), the exposure, the file. Repository text goes through `revealHiddenCharacters()` as in the trust dialog. The Code mode pane holds the choice, sandbox (`not-checked` has its own wording) and `-builtin:codemode`.
- **Whether Code mode reaches a server's tools.** A `codemode` / `codemode-deferred` server's Tools line warns, most decisive first (`mcpCodemodeReachNotice()`): the sandbox failed (the host rewrites the exposure to `deferred`, so tool search reaches them), `-builtin:codemode` (no codemode tool, yet the host keeps the exposure, since `codemodeAvailable` reads only the sandbox, so only an active tool search reaches them), or `autoEnableCodemode: false` under any preference but Always on (the MCP extension never activates codemode then). `mcpEffectiveAutoEnableCodemode()` merges it as `loadMcpConfig()` does: the project file's value where that file is read (`trust.decision === true`), else the global file's, else true; the extension reads it on `session_start`, so it applies to sessions started or reloaded afterwards. The Code mode pane repeats the `autoEnableCodemode` warning under Automatic, naming the file.
- **The Code mode choice lives only here** (ADR 0006): a `ConfigScopeSwitch` of Automatic / Always on that sends `PUT /api/tools/settings { codemode }` through `saveMcpCodemodePreference()`, which shares the overview load's deadline (`withinDeadline()`, 15 s) so a request that never answers cannot keep the switch disabled. It applies to sessions started afterwards and reloads nothing: pi applies `defaultTools` when it creates a session, and `reload` carries the tool set pi rebuilt from the previous one, so a reload would only look like it did nothing. The PUT's answer is what the route read back after writing, shown at once, and the overview is loaded again whatever the outcome, since a timed-out save may still land and a refused one may mean the file no longer parses. Unlike the PowerShell switch in General, whose error sits inside its Windows-only block, the save error (`role="alert"`) shows on every platform. Always on is disabled, with the reason as text under the switch (`mcpCodemodeAlwaysUnavailableNotice()`), while the sandbox failed its self-test or the **global** `extensions` set `-builtin:codemode` (`globalBuiltinSettingsPath`); a sandbox nobody has checked yet keeps it available. Never weigh it against `builtinDisabled`, which merges the trusted project's list: Always on writes the global `defaultTools` every project reads, so a project that turns Code mode off for itself would have blocked a choice that works everywhere else, and whether the switch was offered changed with the folder Settings was opened from. `readBuiltinExtensionSwitches()` therefore resolves the global list a second time on its own whenever a trusted project has a list (each switch's `global`); a project-only `-builtin:codemode` keeps Always on available and its Extension line says the choice still applies to sessions in other folders (`mcpCodemodeBuiltinNotice()`), while the row and the Tools lines still report Code mode unavailable for this project's sessions. `/api/tools/settings` gives every refusal a `reason` (`request-denied`, `content-type`, `invalid-request`, `internal`) for the pane to translate; the PowerShell UI still reads only `error`. A project override is said under the switch whether or not it agrees with the global choice, and the `autoEnableCodemode` warnings follow the effective choice (`mcpEffectiveCodemodePreference()`: the project's where it decides, else the global one), while the switch and the sidebar row keep showing the global choice they save.
- **Trust from Settings.** AppShell owns trust: it passes its status for the folder Settings shows (`projectTrustCwd`, the same cwd its dialog trusts) and `openProjectTrustDialog` (the banner's opener too) through `SettingsPanel` to `McpConfig`. The untrusted notice gets Trust… only while the panel's own fresh status says `requiresTrust && !trusted` (`mcpProjectTrustable()`): not for an unreadable `trust.json` (trusting would fail the same way) nor for an explicit `false` on a folder that requires no trust, where POST answers `trust-not-required`; and never without a handler. The dialog fetches its own listing and status as always, and the panel reloads **in place** whenever AppShell's status changes its decision (`projectTrustReloadKey()` in the load effect's dependencies), so after trusting, or after the dialog read a decision made elsewhere, the project's servers and notices follow while the selection stays. Remounting on a `key` would flash Loading over the list and discard the pane's state, such as a Code mode save under way. **The other sections follow too.** Settings keeps every section it has shown mounted (hidden), and before this a trust could not change while it was open (the banner sits under its backdrop), so Skills and Plugins kept saying "not loaded" with the Project scope disabled after a trust from MCP. `SettingsPanel` passes the page's status to every section whose answer depends on trust, and each reloads in place when `projectTrustReloadKey()` (`components/settings-ui-helpers.ts`) changes: Skills and Plugins their list (a second effect, so the cwd effect still does the first load and the selection and update checks survive), Agents its model list (`GET /api/models` leaves out an untrusted project's extensions). Models takes nothing: models.json, auth and `/api/models/enabled` (`SettingsManager.create()` without a trust option) do not follow trust. They stay keyed on `cwd` alone, since a remount would drop an install under way or a profile draft. The dialog renders after Settings in AppShell and stacks above it (`.project-trust-backdrop` z-index 1100 over 1000).
- **Escape stacking** (`lib/stacked-dialog.ts`). Settings closes on an Escape that reaches `document` in the bubble phase with `defaultPrevented` unset (`listenForPanelEscape()`). A dialog above it (`openStackedDialog()`) listens on `document` in the **capture** phase, which runs before every bubble-phase listener, marks the key handled and calls `stopPropagation()`: one Escape closes only the dialog, and no bubble-phase listener sees it, including any that does not check `defaultPrevented`. Gating Settings on a dialog-open flag instead would have left every other bubble listener firing. The window-level Stop-agent shortcut (`handleGlobalEscape()` in `hooks/useKeyboardShortcuts.ts`) now skips an Escape that is `defaultPrevented`: it used to check only for a textarea or input, so the Escape that closed Settings (or the Mermaid viewer, which only calls `preventDefault()`) with focus on a button also stopped a running agent. The trust dialog ignores Escape while trusting, like Cancel and the backdrop, but still stops it, and an Escape that cancels an IME composition (`isComposing`, or Safari's keyCode 229) is stopped without closing anything. Settings leaves such an Escape alone too, unhandled, so the input method keeps it: closing would have thrown away an Add draft typed with Pinyin. Focus moves to the dialog element itself (`tabIndex={-1}`, no outline: a screen reader reads its title, and a stray Enter presses nothing) and back to the opener on close when the opener is still on the page. After a successful trust that opener, Trust…, goes away with its notice once the panel reloads, and the browser drops focus to `body` behind the modal; McpConfig then moves it to the selected sidebar row (`focusIfLost()`, only when focus fell to the page; `ConfigSidebarItem` passes a `ref` to its button), or, with no row selected (the add pane open, the list empty), to the Add MCP server action (`focusFallback()`; `ConfigListAction` passes its `ref` on too), which every focus fallback of the panel ends at. `lib/stacked-dialog.test.mjs` pins the phases with a dispatcher that follows the DOM's capture/target/bubble order (registration order either way, busy, IME, focus), with the real `handleGlobalEscape()` on the window.
- Strings are `mcp.*` (`state`, `stateShort`, `stateDetail`, `detail`, `signIn`, `exposure`, `unavailable`, `trust`, `group`, `footer`, `codemode`), reusing the trust dialog's shared `mcp.server.*`, `mcp.field.*`, `mcp.fileProblem.*` and `mcp.reason.*`; keys picked at run time sit in literal maps in the helpers so the translation test can find them. Styles are `.mcp-*` in `app/settings.css`; `MobilePwaLayout.test.mjs` requires every `.mcp-*` rule to match a class the panel (McpConfig, McpSignIn, McpAddServer) renders and back. The add pane's words are `mcp.add.*`, the importer's `mcp.importNote.*` (84 codes and their variants), `mcp.importProblem.*` and `mcp.importField.reason.*`.

## Settings › MCP writes (`lib/mcp-config-file.ts`, `POST /api/mcp`)
- **Every `mcp.json` write goes through `lib/mcp-config-file.ts`**, never the SDK's `add/update/removeMcpServerConfig()` (the internals adapter loads them only for the contract test): those write in place with `writeFileSync`, with no lock, no atomic replace, no mode, and an untyped throw. The writer keeps their semantics byte for byte — parse (no BOM stripped), apply the edit to the parsed object, write the whole document back with the indentation of its **first indented line** (`"  "` when none) and **always** a trailing `\n` (whatever the file had), `enabled: true` and `exposure: "codemode"` delete their key, unknown keys at both levels stay, CRLF and compact arrays are rewritten as the SDK rewrites them — and `lib/mcp-config-file.test.mjs` compares its bytes with the SDK editor's on every fixture and operation, so an SDK change fails the test. It differs only where the SDK would write for nothing: an edit that changes nothing (switching on a server that is on) leaves the file's bytes alone. Server names are read with `Object.hasOwn()` and written with `defineProperty`: a plain `servers[name]` for `__proto__` returns `Object.prototype`, and a patch would then write `enabled` into every object in the process.
- **Lock, then atomic replace.** Writes to one real path run in a globalThis queue (`Symbol.for("pi-web:mcp-config-write-queue")`), so Pi Web's own writes never wait on each other's lock, and under a proper-lockfile lock on `<real path>.lock` (`realpath: false`, about 3 s of retries, then a typed `locked`) for other Pi Web processes; the pi CLI writes without a lock, so nothing serializes against it. The new text goes to `.<name>.<uuid>.tmp` beside the **real** file, `wx` and 0600 while written, then `chmod` to its final mode and `rename` over the real path, so a reader (an MCP host syncing before a prompt) sees the old file or the new one, and a symbolic link stays a link. Writing to the configured path instead would replace a dotfiles link with a regular file. Modes: the **global** file is always 0600 (it may hold literal secrets) and a folder created on the way 0700; the **project** file, often committed, keeps the mode it had (`chmod`, not the umask) and is 0644 when new.
- **Where it writes.** The global file is the user's: a link is followed wherever it leads, a dangling one by hand to the file it names, which the write creates. The project file is the repository's and follows the reader's link rule — `locateProjectMcpConfig()` and, for a file that does not exist yet, `projectMcpConfigCreatePath()` in `lib/mcp-config-read.ts`: the real path, a link in the file or in `.pi/` included, must be inside the allowed roots, and a dangling link (file or `.pi`) is refused rather than taken for a missing file, or a cloned repository could aim the write anywhere. The file is read through `readResolvedConfigFile()` (`O_NOFOLLOW | O_NONBLOCK`, `fstat`, 1 MiB for the project). Every refusal is an `McpConfigWriteError` (told by a `Symbol.for` brand, so a second module copy still counts) whose `reason` the route passes on as a 409 — `unparsable` (the message never quotes the file: `jsonErrorMessage()`), `invalid-shape`, `server-missing`, `name-taken`, `link-dangling`, `link-outside`, `not-a-file`, `too-large`, `locked` — with the file left untouched; `unreadable` is a 500 `internal`.
- **`POST /api/mcp`** takes `enable` / `disable` / `remove` (`{ scope, name }`), `set-enabled` (`{ enabled, servers: [{ scope, name }] }`, one write per file and a `results` entry per server, so a refused one leaves the rest switched) and `undo` (`{ token }`), each with the panel's `cwd` when it has a project, and answers with the overview GET would give (plus `undo`, `restored` or `results`), so the panel replaces its listing without a second request. Guards, in order: `isApiRequestAllowed` (403 `request-denied`), JSON content type (415), a JSON object (400 `invalid-request`), the cwd as GET checks it (`validateMcpProject()`, shared with Test, sign-in and `/api/project-trust`: `cwd-invalid` for an empty or relative path, `cwd-denied` for one outside the allowed roots, a `..` or a folder that does not exist, then `cwd-not-directory`), then **MCP off makes the server list read-only** (409 `mcp-off`, `mcpInternalsOrRefusal()` in `lib/mcp-entry-request.ts`, which Test and sign-in share) — `PI_WEB_DISABLE_MCP` (the operator's word, and the pi CLI reads the same files) or SDK modules that cannot load (nothing can be checked) — but **not** `-builtin:mcp`, and not the Code mode choice in the same panel, which belongs to the separate codemode built-in and is saved through `/api/tools/settings`, which a project can reverse: whether a global switch works must not depend on the folder Settings shows. A project server needs the cwd (400) and a decision, exact or inherited, that trusts the folder (403 `project-untrusted`; an unreadable `trust.json` 409 `trust-unreadable`): the MCP host's `mayReadProjectConfigNow()` rule, never `trusted`, which a fresh folder has with no decision. Turning on an entry that references `PI_WEB_PASSWORD` is refused (409 `web-password`, checked under the lock on the entry as it is then); turning it off and removing it work. An entry that is not an object (`"name": "text"`, `null`, an array) has no `enabled` to write: switching it is refused as `entry-not-object` (409, a `setMcpServersEnabled()` outcome of its own, `not-an-object`), never reported as `server-missing`, which would tell the user the file no longer defines it; Remove works. The reader marks such an entry `notAnObject` (its `enabled` reads true), so the panel never offers its switch. The edit itself runs under the lock, so a server removed or renamed since the listing gets `server-missing`, never a stale write.
- **Undo** (`lib/mcp-undo.ts`). A removal hands the raw entry and its index to a globalThis map (`Symbol.for("pi-web:mcp-undo")`, at most 100, oldest first) under a `randomUUID()` token with an unref'd 60 s timer whose cleanup deletes only the record it was set for; the response carries `{ token, scope, name, path, expiresInMs }` — remaining time, not a timestamp, so the browser's clock does not matter — and never the entry, which may hold literal secrets. `undo` takes the record once (a second click gets 410 `undo-unavailable`), re-checks a project's folder and trust as any write, and puts the entry back **where it stood** (`insertMcpServer()` with the index, rebuilding `mcpServers` in place so its position in the file stays), byte for byte when nothing else changed. A name the file defines again since is never replaced (409 `undo-name-taken`); a failed undo hands the record back for the time it had left, so it works once the cause is gone. It restores the entry as it was, a `PI_WEB_PASSWORD` reference included: undo returns the file to what it held a moment ago, and the panel shows such an entry as refused. A server restart drops pending undos.
- **The panel** (`components/McpConfig.tsx`): a server's detail header holds Remove and its switch (`ConfigDetailActions`, as Plugins does; a sidebar row is a button and cannot hold one), and under them a note both point at with `aria-describedby`: why they cannot be used (`mcp.reason.<block>`, from `mcpWriteBlock()`: `mcp-off`, `project-untrusted`, `trust-unreadable`; `entry-not-object` for an entry that is not an object; or `web-password` for the switch of such an entry while off), or under `-builtin:mcp`, which leaves the files writable, "Changes are saved to the file, but no session connects these servers", so the note never contradicts the banner; while the controls simply work there is no note, and the switch points at nothing (hosts read the files before every prompt, so a change applies at each open session's next message). The group heading's `n/m` count became `ConfigSidebarGroupSwitch`, described by the banner that blocks it — the MCP-off notice and the trust notice each add a sentence saying the servers cannot be changed here, and carry an `id` (`ConfigNotice`, `ConfigTrustNotice`, `ConfigSwitch` and `ConfigSidebarGroupSwitch` take `id` / `describedBy`). Switching a group on never sends an entry that references `PI_WEB_PASSWORD`, and no switch sends one that is not an object (`mcpGroupSwitchTargets()`); the note says how many PI_WEB_PASSWORD entries stayed off, and what the route refused goes under the heading (`ConfigSidebarGroupStatus`). **The switch reads on by `mcpGroupSwitchChecked()`, passed as `checked`, not by `enabled === total`:** some server is on and every server it *can* turn on is. With the plain rule a group holding a switched-off PI_WEB_PASSWORD entry stayed partial for good, so the switch always read off, every click asked to turn the group on and sent nothing, and the group could never be switched off from its heading. The `n/m` count still counts the file. Remove shows a notice with Undo until `expiresInMs` runs out, and focus moves to Undo when the removal took the focused pane with it, and to the selected row when the notice goes (`focusIfLost()`). One write at a time: every switch, Remove, Undo and Refresh wait while a change, a Code mode save or a load is on its way, and both Code mode options wait while a server change is (a change's answer carries the Code mode choice as read before a save still on its way, and `applyOverview()` would put it back over what the save had applied); a change's answer drops a load still on its way (it may predate the write). Waiting disables the pressed control, and a focused element that becomes disabled loses focus to `body` behind Settings: each handler notes the focused button before the change (`pressedButton()`) and hands it back as `focusBack` once answered, and the view gives it focus once nothing waits any more — after a refused change's reload too — or the selected row when the control went away or stays disabled (`focusAfterChange()` in `lib/stacked-dialog.ts`, only when focus fell to the page). A removal or an undo that worked does not: its focus goes to Undo and to the restored row, from effects declared before that one. Any refusal or timeout loads the overview again, because the file may no longer say what the panel showed and a change that timed out may have landed. The POST carries the cwd only when the listing covers the project: after a `cwd-*` refusal it would refuse global changes too. `postMcpAction()` shares the 15 s deadline (`withinDeadline()`).
- **Never exercise these writes against the live dev server or a real `~/.pi/agent`**: `app/api/mcp/route-write.test.mjs` runs every action against a `PI_CODING_AGENT_DIR` in a temp folder.
