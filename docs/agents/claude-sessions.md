# claude sessions (#250, #253, #270, #272)

pi-web can run a session on the **claude** harness instead of pi: a `claude -p` child process per live session — the **system claude**, with the user's own config, login and `CLAUDE.md` — translated into pi-web's existing session events. pi sessions are untouched; everything below applies only to rows whose `harness` is `"claude"`.

Files: `lib/claude-shared.ts`, `lib/claude-argv.ts`, `lib/claude-config-dir.ts`, `lib/claude-index.ts`, `lib/claude-adapter.ts`, `lib/claude-subagent-view.ts`, `lib/claude-session.ts`, `lib/image-attachments.ts` (the claude image whitelist and `validateClaudeImages()`), `lib/agent-language.ts` (the Agent language and the one fixed instruction `--append-system-prompt` carries,), `lib/agent-language-config.ts` (the server setting a new session captures), `app/api/claude/route.ts`, the claude branches of `app/api/agent/**` and `app/api/sessions/**`, `instrumentation-node.ts`, the claude parts of `hooks/useAgentSession.ts`, `components/ChatInput.tsx` (`ClaudeComposerControls`, the claude model list, the claude effort entries `CLAUDE_EFFORT_ENTRIES`, the claude image gate `filterComposerImageFiles()`), `components/HarnessSelector.tsx`, `components/ChatWindow.tsx`, `components/ClaudeSubagentRow.tsx`, the claude anchor in `lib/message-display.ts`, `components/SessionSidebar.tsx` (`HarnessMarker`), `components/AppShell.tsx`, `claude.*` and `claudeSubagent.*` in `lib/i18n/messages/*`.

## Choosing the harness
- A fresh composer's bottom bar carries, left to right, the attach button (both harnesses,), the **harness selector** (`HarnessSelector`: a popover with the model selector's toolbar button and menu rows, **pi** — the default, unchanged — or **claude**) and **the one model selector**. The model selector's list follows the harness: pi's models as before, or claude's four full names, `claude-opus-5-5` / `claude-sonnet-5-5` / `claude-haiku-5-5` / `claude-fable-5-1` (`CLAUDE_MODELS` in `lib/claude-shared.ts`, pinned to the models claude **2.1.312** offers; nothing is discovered at runtime, no alias and no "claude default" entry). Switching the harness resets the destination's model: claude → `claude-opus-5-5` (`DEFAULT_CLAUDE_MODEL`), pi → no override, so pi's default model is selected again.
- Under the selectors, while claude is chosen, one line: "Uses the system claude; if something goes wrong, adjust claude from the pi-web terminal." (zh-CN 「使用系统 claude；如有问题，请在 pi-web 终端手动调整 claude」, zh-TW 「使用系統 claude；如有問題，請在 pi-web 終端手動調整 claude」, key `claude.systemHint`); nothing for pi.
- **Model, effort and compact (; this rewrites #250's "fixed for the session's life").** A claude composer uses pi's own toolbar controls in pi's slots: the model selector (`ModelSelector`, claude's four full names, the current one selected), the reasoning button and its `SelectorRow` menu for claude's **effort** — exactly `low` / `medium` / `high` / `xhigh` / `max` plus 「默认」 (en `default`, zh-TW 「預設」; "No --effort: your claude configuration decides"), one active entry, a description per entry, no star, no `off` / `minimal` / `auto` (`CLAUDE_EFFORT_LEVELS`, `CLAUDE_EFFORT_DEFAULT` in `lib/claude-shared.ts`) — and, in an open session, pi's compact button. A fresh claude composer offers model and effort (no compact; nothing to compact yet), its effort pick seeds the created session, and its system-claude hint stays as it was. At ≤640 px an open claude session keeps the model selector in the bottom bar's left cell, right after the attach button, exactly where pi's sits; effort and compact sit in the composer's existing More controls menu, and opening and closing it changes nothing else (owner 有意变更: this moves only the model selector back out of #272's phone menu). The harness stays fixed: an open claude session has no harness selector, and the #250 "claude · <model> — fixed for this session" line and its `claude.fixedLine` key are gone.
- The three controls are usable only while the session is idle: they are rendered disabled while a turn or a compaction runs and until the page's event stream has said whether one runs; the server refuses `set_model` / `set_effort` / `compact` mid-turn ("A claude turn is running; … when it ends") and changes nothing.
- A switch claude refuses shows one visible line under the selectors, a localized prefix plus claude's own text — "Could not switch model: <claude's error>" (zh-CN 「无法切换模型：」, zh-TW 「無法切換模型：」; an effort refusal "Could not change effort: …"); the selector, the list row, the detail and the index keep the old model, and the next successful switch replaces the line. The control shows a new value only once the server accepted it.
- `PATCH` takes only `{ name }` / `{ archived }`.
- `POST /api/agent/new` takes `harness: "claude"` and `model` (required, one of the four full names; a bare alias such as `sonnet` is refused 400), optional `effort` (a level or `"default"`; anything else 400 before any record or child; absent means the default) with type `prompt` or `ensure_session`; a #219 `claudePreset` is dropped unread. The order is the guard's: validate the fields, `isRegistrableRoot(cwd)` (the pi route's refusal and reason), claude on `PATH`, then the index entry and the first child. Nothing is created before the guard passes. The reply's model is `{ provider: "claude", modelId: <full name> }`.
- `claude` is resolved from `PATH` only, on every call (`findClaudeBinary()`); there is no path setting and nothing bundled. `GET /api/claude` reports `{ available, reason?, models, defaultModel }` (the four full names and `claude-opus-5-5`) without creating anything; when claude is missing, the harness menu's claude row is disabled and the reason is visible text under the selectors.

## argv (`lib/claude-argv.ts`)
One reduced set for every child, the model passed verbatim:

| launch | argv |
|---|---|
| first | `-p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --model <full name> --permission-prompts none --session-id <id>` |
| restart | the same with `--resume <id>` instead of `--session-id <id>` (once claude has a transcript for the id) |
| effort | `--effort <level>` right after `--model`, on every launch, when the session's effort is not 「默认」; the default entry passes no `--effort`, so its argv stays the 13 words above |
| Agent language | `--append-system-prompt <instruction>` after `--model` / `--effort` and before `--permission-prompts`, on the first launch and every resume, when the session's Agent language is 中文; the instruction is `AGENT_LANGUAGE_INSTRUCTION` in `lib/agent-language.ts`, byte for byte the text pi sessions append to their system prompt. An English session (and every pre-#293 record) passes nothing: its argv is exactly the rows above, with no "reply in English" flag |

Every launch reads the index record, so `--model` and `--effort` are always the session's current values (a model switch or effort change made earlier included), and `--append-system-prompt` follows the language the record fixed at creation.

No `--bare`, `--strict-mcp-config`, `--disable-slash-commands`, `--permission-mode`, `--tools`, `--allowedTools` or `--cwd`: claude's tools, MCP servers, hooks, plugins, permission rules and the session folder's `CLAUDE.md` are the user's claude config's. The session folder is the spawn's working directory. `--permission-prompts none` stays so an action that would ask for permission is denied by claude instead of leaving the turn waiting; the denial reaches the page as a tool error (no approval UI). The #219 tool presets (`read-only` / `writable`) and their flag sets are retired; pi-web lists no claude tools (`get_tools` and the detail's `toolNames` are empty).

## Environment and config dir (`lib/claude-argv.ts`, `lib/claude-config-dir.ts`)
- The child's env is pi-web's minus `PI_WEB_PASSWORD` and `CLAUDECODE` (`buildClaudeEnv()`), by name; nothing is set. The user's `ANTHROPIC_*` and `CLAUDE_*` variables reach the child, and `CLAUDE_CONFIG_DIR` only when pi-web itself inherited it. pi-web never reads, logs or displays a credential.
- Transcripts live where the system claude writes them: the inherited `CLAUDE_CONFIG_DIR`, else `~/.claude` (`claudeConfigDir()`). pi-web creates nothing there; it finds a session's transcript by id and, on delete, removes that one file.
- The #219 dedicated config dir (`~/.pi/agent/claude` by default) is no longer created, read, migrated or deleted, and Settings › General no longer shows a config dir; it may be removed by hand. A failed turn (an authentication error, a child that exits) shows claude's own text plus `(claude config dir: <path>)` as an error notice.

## Index, list and history
- pi-web keeps its own index, `<pi agent dir>/claude-sessions.json` (`lib/claude-index.ts`): `{ id, cwd, name?, model, effort, agentLanguage, created, modified, firstMessage, usage, archived? }` (`model` a full name — the session's current model, rewritten by an accepted switch; `effort` a level or `"default"`; `agentLanguage` `"en"` or `"zh-CN"`, the server's Agent language when `POST /api/agent/new` created the record, never rewritten by a later setting change; no preset), written whole per change (serialized per file, temp + rename), each write bumping the session list version. A missing or corrupt file reads as empty. The claude session id is pi-web's id.
- The reader is tolerant: `model`, else #219's `modelAlias`, mapped to a full name (`opus` / `claude-default` → `claude-opus-5-5`, `sonnet` → `claude-sonnet-5-5`, `haiku` → `claude-haiku-5-5`); a legacy `preset` is ignored and an unrecognized value reads as `claude-opus-5-5`, so no record is dropped (only `id` and `cwd` are required). A record without `effort` (every pre-#272 record) or with an unknown one reads as `"default"` (`normalizeClaudeEffort()`); one without `agentLanguage` (every pre-#293 record) or with an unknown one reads as `"en"` and launches without `--append-system-prompt`. Reading never rewrites the file; the next index write stores every record in the new shape (`model` + `effort`, no `modelAlias`).
- `GET /api/sessions` adds those rows (`harness: "claude"`, `claude: { model, effort }`, `archived`; the detail's `info` and `POST /api/sessions/stats` carry the same current model) beside the pi rows; nothing scans claude's projects directory, so a claude session created outside pi-web is never listed, and nothing is written to the pi sessions store.
- A claude session's sidebar row (active and archived) shows only the harness chip `claude`: it is the last element of the title line, pushed to that line's right edge, the title ellipsizes first and the `filtered` chip stays beside the title. No model name appears anywhere in the row — text or tooltip. pi rows carry no harness marker. The row still keeps `data-harness="claude"`.
- History is claude's own transcript, `<config dir>/projects/*/<id>.jsonl`, found by id and read through the adapter (`GET /api/sessions/[id]`): no parallel event log exists. The detail has no branch tree; `snapshotRevision` is null (the transcript grows behind pi-web).
- Subagent runs come back from claude's sidecars: `<transcript dir>/<id>/subagents/agent-<agent id>.jsonl` and its `.meta.json` (`claudeSidecarFiles()`), read by `readClaudeHistory()` and served as the detail's `claudeSubagents`. The main transcript keeps the `Agent` call and its tool result; the run is linked to its sidecar by the receipt's `toolUseResult.agentId`, else by the meta's `toolUseId`, and nested sidecars are followed the same way (no depth cap). The sidecar's opening prompt is the run's prompt, not a timeline entry; sidechain entries never enter the main list. claude's `<task-notification>` turn (`turnOrigin: task_notification`) gives the run's final status, `<result>` and usage, and becomes a hidden `claude:task-notification` anchor instead of a user bubble. A missing or unreadable sidecar leaves its run without entries, silently. Entry ids are claude's `uuid`, the same on the live stream, so live and history yield the same entries and merge by id.
- The page (`hooks/useAgentSession.ts`) keeps one run map per session, by tool call id: every session read seeds it from `claudeSubagents` and every `claude_subagent` event merges into it, both through `lib/claude-subagent-view.ts` — an entry id already held keeps its place (a history read's copy wins), new ids append once, a settled status never returns to running. A reload in the middle of a run therefore shows the entries already on disk once and appends the later live ones; a session without the field keeps an empty map.
- **The Agent row** (`components/ClaudeSubagentRow.tsx`; `components/MessageView.tsx` renders it for an `Agent` / `Task` call that has a run, `components/ChatWindow.tsx` hands the runs down through `ClaudeSubagentContext`, so a pi session and a claude call without a run keep the ordinary tool card). Collapsed it is one header line with a subagent-colour bar: the `subagent_type` badge, the description, then while running the latest progress description and "Running", once settled the state when it is not "completed" and `N tools · duration · tokens` from claude's task statistics. State changes show in the header only; timeline entries are append-only. Expanded it shows, in place, the prompt (whole, in a scrollable block), the indented timeline — every step rendered by the chat's own `MessageView`, tool results under their calls — and, once settled, the Result (the run's final reply shows once, there; "No result" when claude reported none). Nothing of the body is mounted while collapsed. The first 25 steps show, then "Show N more" reveals the rest: nothing is truncated or hidden. A nested `Agent` call in the timeline is the same row, at any depth.
- Expansion: a row never toggled is open while its run is running, failed or interrupted (claude's killed/stopped/cancelled statuses) and closed once it completed; a manual toggle wins over every later state change, kept in page memory by tool call id (never stored), so it survives the row moving from the stream into the list and into the folded process details. A toggle changes nothing else: no message, composer or stream state, and the focus stays where it was.
- Strings: `claudeSubagent.*` in `lib/i18n/messages/{en,zh-CN,zh-TW}.ts` (running / failed / stopped, tool count, tokens, Prompt, Result, No result, Show N more).
- `PATCH /api/sessions/[id]` takes `{ name }` and `{ archived }` for claude rows (index only); the sidebar's archive set mirrors the index for claude rows and keeps the browser set for pi rows. `DELETE` ends the child, then removes that session's transcript and index entry, nothing else.
- Usage is the sum of each turn's `result` aggregate (input, output, cache read/write, cost), recorded in the index and served by `GET /api/sessions/[id]` `stats`, `POST /api/sessions/stats` and `get_session_stats` — never the streamed per-message usage, which under-counts.

## Lifecycle (`lib/claude-session.ts`)
- One `ClaudeSession` per live child in a `globalThis` registry. It implements the event-stream session shape, so `GET /api/agent/[id]/events` hands it to `createAgentEventStream()` unchanged; opening the stream starts a child when none is alive.
- The child lives while a page renews the lease (`POST /api/agent/[id]/lease` renews, never spawns) or a turn runs, and ends one `PI_WEB_IDLE_TIMEOUT_MS` after the last renewal (`0` disables). It runs in its own process group (`detached`), which is what shutdown signals: stdin closed, SIGTERM, SIGKILL after 3 s; any descendant left after the leader exits is killed too. `instrumentation-node.ts` ends every group on SIGINT/SIGTERM.
- The next open or send after an exit starts `claude --resume <id>`: the same conversation, its history read from the transcript.
- Commands answered for a claude id: `prompt` (one turn at a time: no queue, no steer; the composer keeps Send disabled with a visible reason while a turn runs), `abort`, `get_state` (`model` and `claudeEffort` from the index record as it is now, `isCompacting` during a compaction), `get_tools`, `get_commands`, `get_session_stats`, and since `set_model` (`{ model }`, or pi's `modelId`, one of the four full names), `set_effort` (`{ effort }`, a level or `"default"`) and `compact`. A malformed switch is 400. Every other command (`set_thinking_level`, `set_tools`, `fork`, `navigate_tree`, `steer`, `follow_up`, `reload`, …) is refused (400, "not available for claude sessions") and starts nothing.
- **Model switch.** With a live child, `set_model` writes claude's own `control_request` `{ subtype: "set_model", model }` on stdin (`claudeSetModelLine()`) and waits up to 15 s (`CLAUDE_CONTROL_DEADLINE_MS`) for its `control_response`: accepted (`{ model }`), the index records the model and the same child and transcript go on — no restart, no resume — and the next turn's assistant `message.model` is the new model; refused (claude's `check_failed` "… model not changed", or no answer in time), the reply is `{ model: <old>, rejected: true, error, errorCode? }` and nothing changes. With no live child the switch is the index's alone (`{ model, pending: true }`, nothing spawned) and the next open or prompt resumes with `--model <new>`; so does a child that exits before it answers (the switch is recorded the same way, `{ model, pending: true }`). A child is not idle-reaped while a control request waits for its answer.
- **Effort change.** A level goes to the live child as `control_request` `{ subtype: "apply_flag_settings", settings: { effortLevel } }` (`claudeSetEffortLine()`), which the recording proves reaches the next request (`effort/runtime-probe.jsonl`), so the child and the conversation stay; the index records it for every later spawn. The default entry has no in-place value: picking it records the index and ends the idle child, so the next one starts without `--effort`. With no live child, or one that exits before it answers, the change is the index's alone (`{ effort, pending: true }`).
- **Compaction.** `compact` writes claude's own bare `/compact` user line (`claudeCompactLine()`, no instructions) as a turn: no other prompt or switch is taken meanwhile, the page gets pi's `compaction_start` / `compaction_end` (not a reply: no assistant message is shown for it), and the command resolves when that turn's `result` arrives — `{ tokensBefore }` from claude's `compact_boundary` (`compact_metadata.pre_tokens`), `{ aborted: true }` after Stop, claude's own error otherwise (also when claude ended the turn without compacting). It never restarts, resumes or appends instructions. The composer's result slot then shows one line with only claude's number, "Compacted from N tokens" (zh-CN 「已压缩：压缩前 N tokens」, zh-TW 「已壓縮：壓縮前 N tokens」, `claude.compactResult`) — no after or saved figure; a failed compaction shows its error in the same slot. While it runs Send is disabled with "claude is compacting; …", and the compact button is pi's Stop compaction, which sends claude's `abort` (the interrupt below): the turn ends stopped, without a marker or summary, and the session takes the next message.
- Stop writes the stream-json interrupt control request; a turn still running after 5 s gets SIGINT on the process group. The partly streamed reply stays as a final message, the turn ends `aborted` (no error notice), and the session takes the next message.
- A turn's end emits `agent_end`, `agent_settled`, `prompt_done` (the running indicator, completion sound and notification follow them as for pi) and records the `result` usage.
- A background subagent leaves the session **unsettled** from its `Agent` call until claude's own follow-up turn starts (`ClaudeStreamTranslator.hasUnsettledSubagents()`): the idle timer does not reap the child meanwhile, the lease reply and `GET /api/agent/running` (`subagentsActiveSessionIds`) report `subagentsActive`, and a turn ending meanwhile carries `subagentsActive: true` on `agent_settled` / `prompt_done`, so the page holds its chime and notification and the server sends no completion push. claude announces a finished background run with `task_notification` and then starts a turn of its own (its next `init`): alone, that is a turn of its own — `agent_start`, the hidden `claude:task-notification` anchor (no user bubble), the reply, its normal end; when it starts while a turn still runs (claude's stdin mode emits the parent's `result` only at the very end), that turn simply waits for one more `result`. Either way exactly one completion is announced, when the last follow-up turn ends. Stop invents no subagent state: a run keeps the last state claude reported.

## Attachments
- Entry points: the attach button, paste and drag-and-drop, identical in a fresh claude composer and an open claude session (and while a claude turn runs, as for pi); paste and drop go through the same `processImageFiles()` as the button.
- Limits are pi's: at most 10 images per message (`MAX_ATTACHED_IMAGES`), each at most 10 MiB (`MAX_ATTACHED_IMAGE_BYTES`); the 11th and an oversized image are not attached, silently, as for pi. claude adds a format whitelist, PNG / JPEG / GIF / WebP (`CLAUDE_IMAGE_MIME_TYPES` in `lib/image-attachments.ts`): any other image (BMP, SVG, …) is not attached and the composer shows one visible line, "Only PNG, JPEG, GIF and WebP images can be attached to a claude session." (`chat.claudeImageFormats`, in all three locales), cleared by the next accepted pick or when the composer is cleared. pi's `image/*` gate, its silent handling and its warning rules are unchanged.
- No client-side resizing: an image is sent as picked. One over claude's own API limit (5 MB) goes to claude's own compression or fallback; if claude fails, its error shows as for any failed turn.
- The server validates before anything is written: for a claude `prompt`, `POST /api/agent/new` and `POST /api/agent/[id]` run `validateClaudeImages()` (array, ≤10, valid base64 within 10 MiB, whitelisted media type) before a record is created or a child started; a failure is `400 { error, code: "prompt_rejected", accepted: false }`, and nothing reaches claude's stdin. pi's path is untouched.
- Transport: one stdin user line whose content is the text block (omitted when there is no text) then one `{ type: "image", source: { type: "base64", media_type, data } }` block per image, base64 and media type exactly as the composer read them (`claudeUserInputLine()`; without images the content stays the plain string). It is byte for byte the line claude 2.1.312 accepted in `lib/__fixtures__/claude-2.1.312/image/stdin.jsonl`.
- Image-only sends are turns. A session whose first prompt has no text is listed with the locale-independent `firstMessage` `[Image]` (`claudeFirstMessage()` in `lib/claude-shared.ts`, used by the server's index record and the client's transient sidebar row); a prompt with neither text nor image is still refused ("A claude prompt needs text").
- Display: the live user bubble carries the images (`claudeUserPromptEvents()`), and a reload maps them back from claude's transcript (`image` blocks with inline base64). pi-web keeps no copy. claude's hidden `isMeta` `[Image: source: …]` companion entry renders nothing. claude's own `/tmp/claude-<uid>/…/images` copies belong to claude and are untouched by pi-web; delete still removes only the transcript and the index entry.
- No "Images may not be sent" warning for any of the four claude models, whatever pi's model list says; pi's rules are unchanged. A claude draft keeps its images like a pi draft, and while a claude turn runs Send stays disabled with the attached images kept.

## The adapter (`lib/claude-adapter.ts`)
The only module that knows claude's formats. `ClaudeStreamTranslator` maps stream-json events to pi events: `stream_event` content blocks → `message_start` / `message_update` (`text_*`, `thinking_*`, `toolcall_*`), each `assistant` event → the authoritative `message_end` (one per content block, as claude emits them; empty redacted thinking dropped) and `tool_execution_start` for its tool calls, `user` tool_result blocks → `tool_execution_end` + a `toolResult` message (`isError` from the block: an auto-denied action is an error result naming the denial), `result` → `agent_end` plus the turn's usage or claude's error. `control_response` events become the answer to the control request with their `request_id` (`claudeControlResponse()`: success with its `response`, or claude's `error` / `error_code`), never a chat message; `compact_boundary` gives the compaction's `pre_tokens`. `claudeTranscriptToMessages()` maps the jsonl transcript to the same messages, entry ids from each entry's `uuid`; claude's transcript `system` / `compact_boundary` entry becomes pi's existing compaction card (`role: "custom"`, `customType: "compaction"`, `details.tokensBefore` from `compactMetadata.preTokens`, no summary body: `components/MessageView.tsx` shows "Conversation compacted" and the token line), at the place claude compacted, with every earlier message still listed. claude's own bookkeeping of a command it ran — the `<command-name>/model…` / `/compact` entries, `<local-command-stdout>` / `<local-command-caveat>` entries and the `isCompactSummary` summary — renders nothing. Contract tests run on real recordings, `lib/__fixtures__/claude-2.1.312/` (provenance and scrubbing in its README; `subagent/` is the background-Agent recording with its transcript and sidecar,; `image/` is the text + PNG turn with its exact stdin line, stream and transcript,; `model-switch/` (a refused and an accepted `set_model`, the next turn on the new model), `effort/` (`apply_flag_settings` and the request metadata showing the effort change) and `compact/` (a real `/compact` with its `compact_boundary` and the transcript marker),; `language/` (a 中文 session's argv with `--append-system-prompt`: an English prompt answered in Simplified Chinese,)). The e2e stub (`e2e/claude-stub/claude.mjs`) logs every stdin line and, with `PI_E2E_CLAUDE_STUB_MODE=image`, answers an image turn by writing the received image block and the `isMeta` companion to the transcript before replaying the recorded `image/stream.jsonl` (transcript before `result`). In every mode it answers `set_model` (a full name: success, later replies on that model; anything else: the recorded `check_failed`) and `apply_flag_settings`, and a bare `/compact` with the boundary written to the transcript before `compact_boundary` + `result`; `PI_E2E_CLAUDE_STUB_MODE=switch|effort|compact` replays the `model-switch/`, `effort/` or `compact/` recording from `PI_E2E_CLAUDE_SWITCH_FIXTURE` / `PI_E2E_CLAUDE_EFFORT_FIXTURE` / `PI_E2E_CLAUDE_COMPACT_FIXTURE`. The unit stub (`lib/__fixtures__/claude-stub/claude.mjs`) has the same modes and replies, its `hang` / `deaf` modes leaving every control request but the interrupt unanswered.

## Subagents
claude's own subagents — an `Agent` (or older `Task`) tool call — are first-class runs attached to the call that started them, never main-conversation messages. The run model is `lib/claude-subagent-view.ts` (client-safe, no format parsing): `{ toolCallId, agentId, agentType, description, prompt, background, status, progress, usage, result, entries }`, entries keyed by claude's entry `uuid`.
- **Live** (`ClaudeStreamTranslator`): every stdout event with a `parent_tool_use_id` is the subagent's — its `assistant` replies and `user` tool results become entries of that run (its `stream_event` partials are not shown); a nested `Agent` call inside starts its own run, at any depth. The `system` task events feed the header: `task_started` (agent id, `subagent_type`, description, prompt, `is_backgrounded`), `task_progress` (the progress description and running statistics), `task_updated` (status), `task_notification` (final status, result, `usage` → tokens / tool uses / duration). Each change goes out as one `claude_subagent` event: the run's header plus only the entries new in it. The `Agent` call's tool result stays in the main conversation; an async launch receipt (`status: async_launched`) names the agent and marks the run background, and is **not** completion: only claude's task events settle a run, and nothing pi-web does (Stop included) invents a state.

## No tool preset, no `configured`
claude sessions have no pi-web tool preset and therefore no `configured` state: pi's tool preset menu (where `configured` means "send no tool override, follow pi's `settings.json` `defaultTools`", see [tools.md](tools.md)) is not offered, and claude's tools, MCP servers and hooks come from the user's own claude config.

## Unsupported pi features
Hidden for claude sessions: fork, edit-from-here, ask-in-new-chat, branch navigation (no tree), compaction recovery (pi's truncation prompt) and automatic-compaction settings, pi's reasoning levels and tool changes (claude has its own model, effort and compact controls, above), steer and follow-up, built-in slash commands (`/mcp` included), background tasks, the pi subagent switcher and side panel (claude's own subagents render in their Agent row instead), title generation. HTML export is disabled with visible text in the toolbar. No permission approve/deny control exists: `--permission-prompts none` denies, and the denial shows as a tool error. A claude turn renders like a pi turn: once answered, its process details (intermediate text, tool calls and results) fold behind the turn's toggle — with one exception: a step whose only displayed blocks are `Agent` / `Task` calls of **background** runs still running renders after the fold, at the turn's top level, so the running subagent stays visible after the parent answered; once its run settles the step returns into the fold. A foreground `Agent` call is an ordinary step, and no other rule changes. claude's follow-up turn starts at its hidden `claude:task-notification` anchor (`isMessageGroupAnchor()`), live and in history alike: it is its own turn, with its own process details, and no user bubble.
