# MCP in sessions

## MCP host (`lib/mcp-host.ts`)
- `createPiWebBuiltinExtensions()` returns `{ extensions, mcpHost }`; `startRpcSession()` passes the host to the wrapper. The host's inline extension reads the global and project `mcp.json` itself and hands the servers it wants to the SDK's MCP extension with `pi.registerMcpServer()`, so the extension's own `loadConfig` stays empty (ADR 0006). It stays inactive unless `/mcp` belongs to `builtin:mcp` (`isBuiltinMcpCommand()` in `lib/mcp-command.ts`, the rule the composer applies too): with `-builtin:mcp`, or a third-party extension that registers `/mcp`, another implementation would connect the servers through its own, unscrubbed transport.
- **Nothing connects until a prompt.** Before a prompt sent while no run is going (`!inner.isStreaming`), the wrapper calls `prepareForPrompt()`: the host diffs `mcp.json` against what it registered, unregisters and re-registers only entries whose canonical JSON changed, then waits up to 10 s for servers still connecting. A server that outlasts one full wait is not waited for again. `before_agent_start` also syncs, without waiting, for prompts that do not come through the wrapper. **An extension command is no run:** pi runs it at the very start of `prompt()` and returns, so `mcpPromptPreparation()` (`lib/mcp-command.ts`) reads the message against the session's extension commands by invocation name, as pi does: another extension's command skips MCP altogether (it waited up to 10 s and started servers for nothing), and the built-in `/mcp` registers without waiting (`prepareForPrompt(signal, { wait: false })`). Never skip the built-in `/mcp`: it looks its servers up among the registered ones, and the host registers them only before prompts, so `/mcp login docs` as a session's first message would answer "No MCP server named".
- **Stop during that wait** aborts it, and the prompt is rejected unsent with `MCP_WAIT_STOPPED_MESSAGE`, so the client restores the draft. It cannot live in `before_agent_start`: pi emits it before the run has an abort signal, and `AgentSession.abort()` does nothing until a run is active. The `abort` command waits for the withdrawn prompt to unwind before it checks `isRunning()`.
- **Connection state comes from the transports.** The extension reports none, so `wrapTransportFactory()` wraps pi-web's transport factory and `watchTransport()` follows each transport it creates (listeners plus own `start`, `send` and `close` on the instance, never a wrapper object: the SDK checks `instanceof StdioTransport`). Ready (`watchConnection()`) means every `tools/list` / `resources/list` / `resources/templates/list` request is answered and a macrotask passed without another page being requested; the extension registers the tools in the microtasks that settle the last list. A transport that closes first, or a factory that throws (such as a `PI_WEB_PASSWORD` reference), is failed. **Every transport of a registration is followed, not only the first** (`attemptFor()` used to skip a settled attempt): an HTTP retry, the reconnect at the next call after a drop, and the extension's `turn_start` reconnect once tokens were stored elsewhere (Settings, `pi mcp login`) each open a new one, the latest speaks for the server (`attempt.current`), and an older one closing late is ignored. The first outcome still settles the attempt, which is all a prompt waits for, and the host still never retries a failed server whose entry is unchanged (ADR 0006): only the extension's own reconnects change its state.
- **What a session sees goes to Settings** (`lib/mcp-status.ts`). Every change of an attempt is written as `{ origin: "session", state, sessionId, cwd, updatedAt, error?, stderr?, conflict?, closedAt? }` under the entry's `scope\0sourcePath\0name` with `mcpConfigKey()` (`lib/mcp-config-key.ts`) of the entry as `loadMcpConfig()` returned it — the validator hands back the parsed value itself, so that is the key GET lists — never of the config the host registered, which `withReachableExposure()` may rewrite. The latest write for the same content wins, a test's or any session's, so a global stdio server shows the last report with that session's folder. A session syncs `mcp.json` only before its prompts, so one still holding an entry from before an edit reports about the old content under the old key, beside the record for the file as it is now, never in its place. States: `connecting` (a transport opened), `connected`, `needs-auth`, `failed`, `disconnected`, `conflict`, `not-trusted`.
  - **needs-auth** is told from the error `start` or `send` rejected with, by name, as the SDK's `needsSignIn()` decides: `McpOAuthAuthorizationRequiredError`, or `McpAuthRequiredError` when the connection passed an auth provider (the factory's third argument, given exactly for an OAuth server; one with an `Authorization` header gets a plain failure). It used to read "failed" with a generic message. A later request that asks for a sign-in reads `needs-auth` too.
  - **disconnected** is a ready transport that closed with nobody calling its `close()`: a stdio server that exited. One the client closed (a reconnect, `/mcp logout`, the session ending) is not news; the host's `session_shutdown` runs only after the MCP extension's handler has awaited every close, so this is what keeps a session's end from reading as drops. The host cannot see the connection itself, so after `/mcp logout` in a chat the record keeps its last state until the next connection asks for a sign-in.
  - **failed** carries the first error `start` / `send` rejected with (a spawn error, an HTTP error) or the server's error answer to `initialize`, else "The connection closed before the server was ready" (a request on a closed transport, `McpConnectionClosedError`, says nothing), and the stdio stderr tail read at close. Error and stderr go through the Test's redactor (`createTestRedactor()` with that transport, for resolved values) and `maskStatusError()` / `maskStatusStderr()`: masked, then shortened. A literal env value a server prints is `•••`.
  - **conflict**: when `pi.registerMcpServer()` refuses, the owner comes from `pi.getMcpServers()`, else from the SDK's words (`already registered by extension "<path>"`); `serverStates()` keeps `not-registered` and adds `conflict`. **not-trusted**: `untrustedProjectServerEntries()` returns the values too, only to hash them into the key; a sync reports at most `MCP_UNTRUSTED_REPORT_MAX` (100) of them and logs the rest as one count, since each is a record in the shared store of 500 and a repository can declare tens of thousands, which evicted the user's Tests and blocked the event loop on every prompt. Every entry is keyed in its own `try`, so one the host cannot key never drops the others or the global servers. Every sync finds these problems again, so each is written only when it changed or its record was replaced since.
  - The host stops recording an attempt it lets go (`letGo()`: unregister, idle release, session end, a reload's dispose) before the extension closes it. Its own record, while nobody wrote another since (`forgetMcpStatus()` / `replaceMcpStatus()` compare by identity), is amended where it would describe a connection nobody holds: `connecting`, which nothing would finish, goes, and `connected` gets `closedAt`, which Settings shows as `on` with "closed that connection at …". Sessions idle out after 10 minutes, so without it most "Connected in a session" rows described closed connections for as long as the server process ran. `failed`, `needs-auth` and `disconnected` stay as they are: still true of the server. At dispose the host also forgets its problem records (`conflict`, `not-trusted`, a refused registration) still its own, and its host-inactive record: those are found again at every sync, and a host that stopped syncing no longer sees them. **The wrapper disposes the host when it starts closing** (`McpHost.dispose()`, once, from `shutdown()` after extension binding and from `destroy()`), before any extension hears `session_shutdown`: handlers run in order, the host's inline extension after the MCP extension and every third-party one, and a close that never returns (a stdio grandchild holding stdout, an OAuth refresh in flight) kept it from ever running once the wrapper disposed at its deadline, leaving "Connected in a session" rows and a host-inactive notice for a session that was gone. The host's own `session_shutdown` handler only repeats the dispose; a released attempt records nothing its transports do afterwards, and a disposed host ignores a late `session_start`. A let-go attempt still settles, for a prompt waiting on it.
  - **A `/mcp` the host does not own**: at `session_start`, an `mcp` command from another extension than `builtin:mcp` records `{ owner, cwd, updatedAt }` under the session id (`recordMcpHostInactive()`, at most 100), forgotten when the wrapper starts closing (the host's dispose), or when a reload starts with Pi's own. Several extensions' `/mcp`, which pi renames `mcp:1`, `mcp:2`, … (the built-in is dropped then too), name the first as the owner; a prompt template named `mcp` is nobody's (`isMcpExtensionCommand()`). `-builtin:mcp` leaves no `/mcp` at all and is read from the files. GET reports the record for the panel's cwd, else the latest of any folder, as `hostInactive`.
  - Tests: `lib/mcp-host.test.mjs` pins each state with fake transports (`drop()` closes one by itself, `close()` as the client; `sendError` rejects a request), the reconnect after a sign-in, masking (a transport failure's message as well as a factory that throws), the let-go rules (a closed mark at idle release and session end, a fresh connection without one, problem records gone at session end), conflicts from the registry and from the SDK's words, recording once per change, a session behind an edit leaving the current entry's test standing, the raw-entry key without a codemode sandbox, and the inactive-host record; its trust fixture checks that `readMcpOverview()` attaches what a session saw (key agreement). `lib/mcp-host.integration.test.mjs` runs a real session: a connected fixture as GET lists it, a killed fixture (`PI_WEB_FIXTURE_PID_FILE`) reads `disconnected`, a crashing server's stderr (and an echoed literal env value masked), a local HTTP server that answers 401 until `mcp-auth.json` holds its token reads `needs-auth` and then `connected` after the next turn, and an inline extension's server of the same name a `conflict` naming `<inline:…>`.
- **Never unregister a server before its transport exists.** The extension assigns `server.connection` only after loading the MCP runtime, and its removal closes that connection; unregistering earlier finds nothing to close, and the extension connects the server anyway with no way left to close it. The host waits (at most `replaceWaitMs`, 5 s) for the transport before unregistering. Once it exists, `close()` is safe even mid-handshake: the connection throws away the client when the handshake finishes. The cap is no guarantee by itself: a plain `mcp_servers_change` does not move the extension's `generation`, so a connection it assigns after the unregister is never closed. The host therefore counts each registration it unregistered without a transport (`abandoned`, by `name\0configKey`), and its factory refuses the next transport asked for one while no live registration claims it (`refuseAbandoned()`): the connection fails and nothing is started. Today the gap is a few microtasks, since Pi Web imports the SDK's `runtime.js` (the same module instance) before any host exists, so `loadMcpRuntime()` is a cache hit.
- A host that has not run for `PI_WEB_MCP_IDLE_MS` (10 minutes; `0` disables) unregisters its servers, unless `ctx.isIdle()` says a run is still going; the next prompt registers them again. The timer is stopped from `agent_start` to `agent_end` and while a prompt waits in `prepareForPrompt()`, and started again at `agent_end`, when `prepareForPrompt()` returns, and whenever a sync finishes. Never rely on `agent_end` alone: a prompt that registers servers and then starts no run (Stop during the wait, a slash command, a rejected preflight) never emits it, and a sync Stop gave up on still finishes in the queue afterwards. A reload binds a new host instance with nothing registered.
- MCP tools register as `mcp__<server>__<tool>`, sanitized to `[A-Za-z0-9_-]` and hashed past 64 characters, so the name cannot be split back: `docs.v2/search.pages` and `docs_v2/search_pages` register alike, and either part may hold `__`. A tool card reads `server/tool` only from its result's details (`{ server, tool }`); a running call, the status line and a codemode script's calls keep the registered name, which is also what scripts call.
- Project `.pi/mcp.json` entries follow the project's trust, as in the pi CLI, inherited trust included: `loadMcpConfig` reads the project file only when told the project is trusted, and the host connects every entry it returns. There is no per-entry approval, because a trusted project's `.pi/extensions` already run inside the same boundary, and earlier (on browsing, not on the first prompt). A project entry replaces a global one of the same name. Without a working codemode sandbox, servers with `codemode` exposure are registered as `deferred`, reachable through `tool_search`.
- **Trust is read fresh on every sync**, through the host's `mayReadProjectConfig(cwd)` option (by default `mayReadProjectConfigNow()` in `lib/project-trust.ts`), never from `ctx.isProjectTrusted()`. That is the wrapper's `SettingsManager` flag: fixed when the wrapper is built — `true` for a folder that needed no trust then — and refreshed only on reload, so a `.pi/mcp.json` that appeared later (`git pull`, `pi mcp add -l`, the model's `write` tool) connected on the next prompt with no trust decision. The read is true only while a decision, exact or inherited, trusts a folder that requires trust — not `getProjectTrustStatus().trusted`, which is `true` for a folder with no trust-requiring resources: `loadMcpConfig` looks at the folder again when it opens the file, and a file landing between the two looks would be read with no decision. Nothing is lost, since `.pi/mcp.json` alone makes a folder require trust. A decision made anywhere, the CLI included, reaches an open session's MCP servers on its next prompt, while its project extensions keep the trust the wrapper was built with until a reload (`/api/project-trust` rebuilds the cwd's wrappers anyway). The cost, twice per prompt (`before_agent_start` and `prepareForPrompt()`), is the SDK's `hasTrustRequiringProjectResources()` (up to 8 `existsSync` in `.pi/`, then one per ancestor for `.agents/skills`) and, for a folder that requires trust, a `lockSync` and read of `trust.json`. An unparsable `trust.json`, or one still locked after the store's ~200 ms wait (synchronous: it blocks the event loop that long), counts as untrusted — fail closed, so connected project servers are unregistered until a read succeeds — with one warning per distinct error, naming the file. The MCP extension's `loadConfig` uses the same read for `autoEnableCodemode`, but the extension calls it only on `session_start`, so that flag follows a trust change only at the next reload. While the project file may not be read, `serverStates()` reports every name it declares as `not-trusted` (problems are keyed by scope and name, since a global entry may share it); the names are read after `loadMcpConfig`, so a file that just landed is reported at once. They come from a file nobody has trusted, so only a regular file of at most 1 MiB whose real path is inside the project is parsed, and only for its `mcpServers` keys: the resolved path is opened once with `O_NOFOLLOW | O_NONBLOCK` and checked through `fstat`, so a link elsewhere is refused before opening, and a FIFO or a device is opened without blocking and never read. `loadMcpConfig()`'s `errors[]` (an unparsable file, an entry the SDK skipped) are logged once per process each instead of dropped, at most 20 per sync and the rest as a count (the dedupe set holds 200 and evicts its oldest, so a file with more errors would log them all at every sync). The SDK words a parse error as `${path}: ${error.message}`, and V8 quotes up to ten characters either side of an unexpected token, often a literal secret, so `scrubMcpLoadError()` (`lib/mcp-json-error.ts`) rewords such a message through `jsonErrorMessage()` before it reaches the log, as the panel does.

## `/mcp` in the composer (`lib/mcp-command.ts`, `hooks/useAgentSession.ts`)
- **Only a bare `/mcp`, and only when pi's built-in owns it.** `handleBuiltinSlashCommand` opens Settings › MCP (`onOpenSettings("mcp")`, AppShell → ChatWindow → the hook, as `/session` does with its panel) when the session's command list has the built-in `/mcp` (name `mcp`, `sourceInfo.path` `builtin:mcp`) or nothing that answers `/mcp` (MCP off, `-builtin:mcp`, Chat-only): `bareMcpOpensSettings()`. Another extension's `/mcp` (the SDK then drops the replaceable built-in) and a prompt template named `mcp` (pi expands it when no extension command has the name) keep the message, which is sent as before. Several extensions' `/mcp` open Settings: pi renames them `mcp:1`, `mcp:2`, … and looks a command up by its exact name, so a bare `/mcp` would run neither and reach the model as the text "/mcp"; the panel's `hostInactive` notice names the first. Every subcommand is sent too: `/mcp login`, `logout` and `reconnect` act on that session's own connections. A third-party input handler that catches `/mcp` cannot be seen from the list.
- **Never guess the owner.** The palette starts `get_commands` as `/mcp` is typed and Enter often comes first, so the case awaits the request under way (`slashCommandsLoadRef`), else uses the loaded list (`slashCommandsRef`, written only through `replaceSlashCommands()`), else asks. Every request and set_tools' clear (`clearSlashCommands()`, which also forgets the request under way) move `slashCommandsGenerationRef` on, and only a request still current writes its answer: a request set_tools outdated used to put back the list of the session it replaced, so after a switch to Chat only another extension's stale `/mcp` kept sending a bare `/mcp` to the model. A failed request is `null`, never an empty list: an empty list is a Chat-only session's and opens Settings, while a list that cannot be read sends `/mcp` as before. Guessing either way would swallow another extension's `/mcp` or spend the host's 10 s connect wait on a message Settings should have taken.
- **Nothing of a prompt happens.** The case returns before `onSend`: no `/mcp` bubble, no `promoteNewSession()` sidebar row in a new chat (the command list still needs the session `ensureNewSession()` builds, as typing `/` does), and `complete()` shows no notice for an `action` (`openSessionStats`, `openSettings`). It works while a run streams: `sendQueued` offers a bare `/mcp` to the handler first and queues it as a steer / follow-up only when unhandled, and `handleSend` lets it through (`offersBuiltinSlashCommandWhileStreaming()`); `canRunBuiltinSlashCommandWhileStreaming()` still lists only the composer's own built-ins. Enter on the palette's built-in `/mcp` submits at once (`submitsSlashCommandOnEnter()`), as Enter does before the list has loaded; other extension commands still complete to `/name ` first, and `isExactSlashCommand()` is unchanged.
- **Focus moves into Settings.** `SettingsPanel` focuses its dialog element (`tabIndex={-1}`, no outline) in a layout effect and gives focus back to the opener on close (`focusModalPanel()`), unless focus went elsewhere meanwhile; on a coarse pointer a text field is not refocused, since that raises the keyboard again. Before, focus stayed on the composer behind the modal, as the textarea is disabled for one render only: the next Escape reached ChatInput's handler first (React listens on `document` and registered before Settings did), stopped a running agent and marked the key handled, so Settings stayed open; typing went into the hidden composer, and a phone kept its keyboard up over Settings. Opened from the sidebar, Settings left focus behind it too, though Escape worked there.
- `lib/mcp-command.test.mjs` pins the rule, `lib/builtin-extensions.integration.test.mjs` the SDK facts it rests on (the built-in's path, its replacement, `mcp:1` / `mcp:2`, and that a bare `/mcp` runs the replacement but reaches the model as text beside two) through a real wrapper, `hooks/mcp-slash-command.test.mjs` runs the hook's own callbacks (outdated requests included), `components/ChatInput.test.mjs` the streaming and Enter paths, and `lib/stacked-dialog.test.mjs` the focus move, with the composer's Escape that used to win.
